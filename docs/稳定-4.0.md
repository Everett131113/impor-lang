# 稳定模式（--stable）设计说明（4.0.0）

这一页回答三个问题：**它挡什么**、**怎么挡**、**挡不住什么**。所有数字都是本机实测，不是设计目标。

## 一句话

打开稳定模式后，任何脚本的**执行预算**（语句条数、墙钟时间、内存、输出、单次分配）都有上限；越界时脚本以一条带错误码（E1020–E1024）、行号、`为什么` / `修复` 的错误退出，而不是把整个进程拖死、把磁盘写满或把内存吃光。

> 不开这一档，行为与 4.0.0 之前完全一致：不计量、不拦截、不改变任何输出。这一档是**可选加固**，不是新的默认语义。

## 五道闸门

| 闸门 | 计量什么 | 默认档 | 严格档 | 错误码 | 触发点 |
|---|---|---|---|---|---|
| 步数 | 执行过的语句条数（三后端可比） | 5,000,000 | 2,000,000 | E1020 StepLimit | 每条语句入口 |
| 时长 | 墙钟秒（含 C 后端与外调） | 30 s | 10 s | E1021 TimeLimit | 每条语句入口 |
| 内存 | 进程工作集 RSS | 768 MB | 256 MB | E1022 MemoryLimit | 每 4096 条语句采样 + 每次大分配前 |
| 输出 | 已写出的字节（按 UTF-8 计） | 8192 KB | 1024 KB | E1023 OutputLimit | 每次 `print` / 日志回调 |
| 单次分配 | 单次请求的元素个数 | 8,000,000 | 1,000,000 | E1024 AllocLimit | 分配**之前**预检 |

两个细节值得单独说，因为它们决定了闸门是「真的」还是「看起来有」：

- **分配前预检**：`arrfill(8000000, 0)`、`list(n)`、`"x" * n`、`arrdup`、`filelines` 都在**真正分配内存之前**算出元素数并判定；等到 `MemoryError` 再从异常里恢复，进程可能已经被系统杀掉。
- **按字节计输出**：中文一个字是 UTF-8 的 3 字节。早先按「字符数」统计时，512 KB 的额度实际写出去 1.39 MB；现在按字节，额度就是磁盘/管道的真实压力。

## 怎么打开

```bash
# 默认档跑一个脚本
python Impor.py run --stable app.impor

# 严格档（作业批改、在线运行台）
python Impor.py run --stable=strict app.impor

# 单项放宽/收紧（可叠加，也可只写其中一项）
python Impor.py run --stable --max-seconds=120 --max-memory=2048 ai_job.impor

# 环境变量（编辑器、CI、批量跑都走这条）
set IMPOR_STABLE=1
set IMPOR_LIMIT_STEPS=20000000
python Impor.py run app.impor
```

| 命令行 | 环境变量 | 含义 |
|---|---|---|
| `--stable` / `--stable=strict` | `IMPOR_STABLE=1` | 打开，并选默认档/严格档 |
| `--max-steps=N` | `IMPOR_LIMIT_STEPS` | 语句条数上限 |
| `--max-seconds=N` | `IMPOR_LIMIT_SECONDS` | 墙钟秒上限 |
| `--max-memory=N` | `IMPOR_LIMIT_MEMORY_MB` | RSS 上限（MB） |
| `--max-output=N` | `IMPOR_LIMIT_OUTPUT_KB` | 输出字节上限（KB） |
| `--max-alloc=N` | `IMPOR_LIMIT_ALLOC` | 单次分配元素数上限 |

**口径**：命令行 flag 覆盖环境变量，环境变量覆盖档位默认值；三者都生效，不是「只认其中一条」。（这条在实现时踩过坑：只读 flag 会让 `run_isolated` 传下来的额度静默失效，自检直接从 8/8 掉到 5/8。）

## 一次执行怎么结束

`impor run --stable` 的退出码是稳定的，CI 可以直接判：

| 退出码 | 含义 | 典型现场 |
|---|---|---|
| 0 | 正常跑完 | — |
| 1 | 脚本自身报错（含 E1020–E1024 熔断） | `10 / 0`、`while true` |
| 2 | 语法/编译错误 | `E2001` |
| 3 | 熔断（子进程围栏判定） | `run_isolated` 超预算 |
| 4 | 原生崩溃 | 解释器自身或 FFI |
| 5 | 超时被强杀 | 围栏超时 |
| 6 | 输出超限被掐断 | 围栏采集上限 |

## 父进程围栏 `run_isolated`

解释器内部的闸门管不到两类事：**解释器自己的 bug**，以及**调进来的原生代码**（`tcc` 产物的段错误、DLL 里的死循环）。这两类只能靠外面一层：

```python
from impor.stability import Limits, run_isolated
r = run_isolated(["run", "app.impor"], limits=Limits(seconds=20), timeout=20, capture_kb=1024)
print(r["kind"], r["exit_code"], r["stderr"][-200:])
```

围栏是一个子进程 + 采集线程 + 超时强杀；子进程的 stdout/stderr 超过采集上限就停止读取并判定 `output-cap`，超时判定 `timeout`，非零退出且带原生异常判定 `crash`。编辑器与批量任务走这条，单脚本调试不必。

## 熔断之后还能继续

熔断是**一次执行**的结束，不是解释器对象的死亡：

- 每次 `run()` 开头重置额度（`begin()`），同一个 `Interpreter` 可以连着跑第二个脚本；
- 跨执行的熔断计数单独记（`trip_counts`），不会被重置，用来观察「这个会话是不是一直在崩」；
- 熔断后继续跑新脚本、内存不累积——6 次反复熔断后 RSS 仍低于 600 MB（有回归测试守着）。

## 内部崩溃怎么留证据

看不见的崩溃最难修，所以两处兜底：

- CLI：未捕获异常写 `~/.impor/crash.log`（超过 512 KB 轮转到 `.1`），并在终端打印路径；
- 编辑器：`root.report_callback_exception` 接管 Tk 回调异常，同样落盘；主循环再兜一层，`KeyboardInterrupt` 退出码 0，其余退出码 1。

`impor stability` 是本机自检：8 个敌意用例（死循环 / 卡死 / 刷屏 / 巨型分配 / 内存累积 / 无限递归 / 除零 / 大整数不误报），全过返回 0，任一失败返回 1，`--json` 给机器读。

## 挡不住什么（诚实边界）

- **只保证失败可控，不保证永不失败。** 稳定模式让「坏脚本」变成「一条错误」，不能让坏脚本变成好脚本。
- **内存是采样，不是硬配额。** RSS 每 4096 条语句采一次，极端情况下会越过上限几十 MB 才熔断；要硬上限请用容器或 Job Object。
- **解释器自身的原生崩溃管不住。** Python 层的 bug、C 扩展的段错误，只能由 `run_isolated` / 容器兜住。
- **不改变语义。** 打开后不重排、不优化、不改输出；只是多了计量与提前判定。所以它也**不会**让慢脚本变快。
- **代价是常数级但可见的。** 同一段 20 万次循环 + 3000 次字符串拼接的负载，本机稳定档比默认档慢约 1.2–1.4 倍（两次实测，每条语句一次预算判断）。这是「用一点速度换确定性」的交易，不是白拿的。
- **不是所有语言都在这条赛道上。** C 的段错误/除零是 UB 的既定规则，Python/Node 的死循环本来就要靠外部超时——它们不给脚本级预算，不是缺陷，是定位不同。对照表见 [`docs/稳定性对照-4.0.md`](稳定性对照-4.0.md)。

## 界面也在这条预算里（4.1 卡死修复）

脚本预算管的是「脚本跑飞」，编辑器还有另一类不稳定：**UI 线程被后台任务拖住**。典型一例是键入 `fib()` 就「未响应」：

- 键入 `(` 会触发参数提示，旧实现直接在 UI 线程调用 `index.definition()`；而工作区索引正在后台全量重建，两者抢同一把锁，界面只能等。
- 旧版删文件时遍历整张引用表（O(文件×名字)），把一次重建拖到数十秒，等待也就变成数十秒。

修复后的两条硬规则：

1. **重建单飞**：`ProjectIndex.refresh()` 拿到闸门才扫描，已有重建在跑时后来者立即返回，不再排队等锁。
2. **UI 线程只用 `probe()`**：不等锁、不触发重建、索引忙时返回空；编辑器随即回退到「只查当前文件」的字符串匹配，提示可能少一条，界面绝不再冻。

实测（无头 Tk 模拟键入 `fib()`）：单键处理 ≤2 ms；键入后空闲期 46.7 s → 4.7 s（探针含 4 s 固定等待）；本工程全量索引 0.69 s（228 个 `.impor`）。回归见 `tests/test_v41_editor_freeze.py`（6 项）。

边界：`probe()` 在索引重建期间会「看不见跨文件定义」，此时参数提示/补全只覆盖当前文件；重建结束后自动恢复。这是拿「短暂的少提示」换「永不假死」，方向是有意选的。

```bash
python Impor.py stability            # 8/8 自检
python Impor.py stability --limits   # 打印两档额度

python tests/test_v41_editor_freeze.py  # 6 项：键入不卡死

```
