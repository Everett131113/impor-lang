# 宽度预算（4.5.0）

"宽度"指标准库模块数与可覆盖的场景面。宽度不是越多越好：每多一个模块，就多一份
三端一致性成本、多一份文档与 conformance 成本。这份文件用来把"该加什么、按什么顺序加"写成可检查的预算。

## 一、成本模型（实测口径）

| 动作 | 一次性成本 | 每个模块的持续成本 |
|---|---|---|
| 只加纯 Impor 模块（无新内建） | 0.5–1 天 | 1 条冒烟用例 + 与 3 个代表模块的 C 对拍 |
| 需要新内建 | +1–2 天（解释器 + C 运行时 + manifest + 基线） | 全量 conformance 复跑 |
| 需要新平台能力（socket/TLS/进程输出） | +3–5 天，且要改 `c_runtime.c` 与 `ctrans.BUILTINS` | 平台矩阵 ×3 |

结论：**优先加不需要新内建的模块**。4.5.0 的 17 个模块全部属这一类，只补了 `ord` / `chr` 两个码点原语。

## 二、当前账面

- 模块数：20 → **37**（+17）
- 公开内建：122 → **124**（+`ord` `chr`）
- 冒烟覆盖：新增 23 条用例（0 失败），代表模块 C 对拍 3/3 逐字节一致
- 未覆盖：新增模块里只有 3 个做了 C 对拍，其余 14 个**只做了解释器冒烟**——这是下一版的欠账

## 三、下一批候选（按性价比排序）

| 优先级 | 模块 | 依赖 | 估算 | 值不值 |
|---|---|---|---|---|
| P0 | `encoding` 补 CRC32 / SHA-256 | 需要 `>>`/`<<` 或环形移位内建 | 2–3 天 | 值：编解码是服务刚需 |
| P0 | `process` 抓 stdout/stderr | 需要管道 API | 3–5 天 | 值：否则 `run` 只能拿退出码 |
| P1 | `csv` 支持引号与转义 | 无 | 0.5 天 | 值：现在的实现只按逗号切 |
| P1 | `http` 客户端 + TLS | 需要 socket + TLS 后端 | 5–10 天 | 值但贵：没 TLS 的 http 只能内网 |
| P2 | `sql` / `pool` 连接池 | 需要 FFI + 驱动 | 10 天+ | 暂缓：FFI 只在 Windows 实测 |
| P3 | `i18n` / `units` 扩展 | 无 | 1 天 | 可延后 |

## 四、什么情况下**不加**

1. 需要改语言语义才能实现的（如"让 `len` 返回字节"）——语义优先，模块让路。
2. 只能在某一个后端跑的（会制造"解释器能跑、exe 崩"的又一类缺陷）。
3. 与既有模块职责重叠且没有明显收益的（`utils` 这种大杂烩一律拒绝）。

## 五、宽度与深度的耦合

宽度上限被深度卡死：同一语义要在「解释器 / Python 转译 / C 全值 / int64 快路径 / IR 下降」× 3 平台上各写一遍，
即 15 个复现点。所以每加一个模块，真实成本是"1 份代码 + 3 份验证"。
4.5.0 起把 IR 下降补上（`impor ir --build`），是为了让后续模块**只需要在 IR 层写一次**，
下降后端负责剩下的事——这是唯一能压低宽度边际成本的结构性改动。
