# Impor 稳定性横向对照（实测）

同一台机器、同一批敌意程序、外部 watchdog 10 秒、stdout 读取上限 1 MB。

判定只看「失败方式」：`contained` 在时限内结构化报错；`hang` 未自行停止、只能被外部强杀；`crash` 原生层异常退出；`output` 输出超限被父进程掐断；`completed` 正常退出。

启动地板（同一引擎跑「什么都不做」的程序，逐次实测）：C (tcc -O2) 0.25s；Impor 默认 0.32s；Impor --stable 0.32s；Node.js 0.22s；Python 3.13 0.09s。下表「耗时」给的是扣掉地板后的运行时间。

| 引擎 | 耗时(s) | 正常跑完 | 相对 Impor 默认 |

| C (tcc -O2) | 0.050 | 是 | 0.04× |
| Node.js | 0.200 | 是 | 0.17× |

读法：稳定模式比默认档慢 1.2 倍（这一步的开销来自每条语句一次预算判断，不是来自重复执行）；换来的是异常脚本在一秒内变成一条带错误码的错误。另外要把两件事分开：Impor 作为树遍历解释器，本身吞吐就比 Python 慢11 倍左右，这是解释器架构的固有成本，不是稳定性带来的。

这一列不做地板扣除：它是端到端时间，能直接拿去和别家比「跑完同一件事花多久」。

## 结论（只写实测支持的）

1. **Impor --stable：5/5 结构化熔断，0 挂起，0 原生崩溃**，最慢一例 1.12 秒退出，且都给出错误码（E1020–E1024）、行号、为什么与修复建议。
2. **其他实现的失败方式**：Impor 默认：1 例未停/强杀、0 例原生崩溃；Python 3.13：1 例未停/强杀、0 例原生崩溃；C (tcc -O2)：2 例未停/强杀、2 例原生崩溃；Node.js：3 例未停/强杀、0 例原生崩溃。C 的崩溃来自「UB 不检查」，Python/Node 的未停来自「没有预算概念」——两者都能被外部超时或容器兜住，但语言自己不提供上限。
3. **Impor 默认档（不开 --stable）与 Python 同档**：死循环会一直跑、刷屏无上限、巨型分配只能等系统处理——所以「更强」不是免费的，必须显式打开稳定模式（或 `IMPOR_STABLE=1`）。

## 这条结论的边界

- 比的是「资源有界、失败可控」，不是「永不失败」：解释器自身/FFI 的原生崩溃仍需 `run_isolated` 父进程围栏兜底。
- Python/Node/C 挂起后都能被容器或超时杀掉，本表说的是「语言自己不提供上限」，不是「无法被运维手段兜住」。
- 内存闸门是 RSS 采样，不是硬配额；极端情况可能越过上限几十 MB 才熔断。
