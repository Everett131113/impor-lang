# Impor 与其它编程语言对比（4.3.1 线 / 2026-11-22）

> 口径先说清楚：**Impor 一列全部是本机/CI 实测、可一条命令复跑**；其它语言一列写的是结构性事实
> （有没有 GC、要不要运行时、生态规模、语言特性边界），不给"同机跑分"——那种数字换个机器就变，
> 而且公开跑分大多是别人机器上的，抄过来只会骗自己。
> 数字出处：`docs/替代记分牌.md`、`docs/能力矩阵.md`、`docs/性能报告-v6.2.md`、`docs/ci-evidence.md`。

## 一、一句话定位

Impor（I++）不是"更强的语言"，它是**交付层语言**：语法收敛到唯一写法（55 个关键字，没有 `func`/`let`/`loop` 这类历史别名），
写起来像 Python，产物是**单文件 exe（中位 126 KB）或 C ABI 动态库**，一份逻辑能被 C / Rust / Python 宿主直接调用。

它的比较对象不是"谁写起来爽"，而是"这段逻辑最后怎么交付出去"。

### 补充：如果目标是“通用系统语言”，按五轴单独判定

上面这句是**当前 4.2 线**的定位，不是“永远不做系统语言”。若把目标换成通用系统语言，竞争轴只有五条：**性能、内存/资源控制、并发、互操作与交付、工具链与生态**。

| 轴 | 当前实测 / 现状 | “最好”的门槛 | 决定性改动 |
| --- | --- | --- | --- |
| 性能 | 解释器 0.17–0.21× CPython（fib 22）；C 后端 fib(28) 42 ms | 同算法同数据结构下 C 的 0.5–2× | 静态类型 + 单态化 + 无装箱 + 栈分配 + LLVM |
| 内存 | GC；无裸指针、无手工释放 | GC / arena / unsafe 三档；峰值可复现 | `Val` 拆值/引用；`own` / `arena` |
| 并发 | 1:1 OS 线程 + 锁 + 原子量 + 条件变量；库级 channel/线程池（真挂起，tcc32 退化轮询） | M:N 协程 + channel；8 核扩展 ≥ 0.9 | 可挂起帧 + 调度器 |
| 互操作 / 交付 | 126 KB exe / 33 ms；C ABI DLL | 一份源码出 exe / dll / wasm / `.h` | 后端多目标化 |
| 工具链 / 生态 | 20 个 std 模块（patch7 增 `std.image`）；VS Code + LSP | syscall 级 std、DWARF、交叉编译、sanitizer | 按 C 的路走，不建包仓库 |

结论：**能，但必须先换内核**——走 script tier / system tier 双档，由类型标注决定档位，而不是继续往动态 `Val` 上叠特性。S1–S6 的执行顺序与硬门槛见 `docs/系统语言五轴路线图-4.2.md`。

在 S1 门槛（system tier 下无装箱、性能 ≥ C 的 0.5×）达成前，对外仍按“交付层语言”表述，不宣称“可替代 C 的系统语言”。

## 三、逐家说清楚

### 1) vs Python —— 同一语法族，但换掉了"分发"

- **同**：缩进块、`def`、`class`、异常、字典/数组，迁移心智成本低；Impor 甚至保留 `except`/`finally` 写法习惯。
- **异**：Impor 的 `build` 出的是**不依赖 Python 的独立 exe**，中位 126 KB、启动+运行 33.2 ms；
  而 Impor 自己的解释器路径要背 CPython 的启动开销（同一批用例中位 247.9 ms，约 7.5 倍）。
- **差距最大的地方**：生态。PyPI 上有几十万包，Impor 只有 18 个标准库模块（v4.3 口径），没有公共包仓库；
  `import math` 这类在解释器/转译器能跑，C 后端直接**编译期拒绝**（能力矩阵第 3 行）。
- **结论**：拿 Impor 替代 Python 只在"脚本要分发给不装 Python 的人"这个场景成立，其它场景替代不了。

### 2) vs C —— 它把 C 当后端，而不是对手

- Impor 的 C 后端只覆盖**可静态翻译的子集**：19 个能力用例 17/19 通过（v4.3 矩阵口径），拒掉的 2 条是"64 位整数溢出"（按设计报错）
  与"标准库 import"（明确拒绝）。它不是"更安全的 C"，因为**不给你指针算术、不给你手工内存**。
- 反过来，C 是 Impor 的宿主：`examples/cabi_demo/host_c.c` 直接 `#include "logic.h"` 链接 `logic.lib`，rc=0。
- **结论**：C 程序员不需要它；需要"写点 C 但别踩内存"的人会喜欢它。

### 3) vs C++ —— 差在抽象工具

- Impor 有类、继承、`interface`/`implements`、`abstract`/`sealed`、异常、闭包；
  v4.2 起还有**声明位泛型**（`def max2<T>(a: T, b: T) -> T`，声明期约束 + 运行期擦除），
  但**没有模板单态化**（不给每种实参类型生成副本、写不了 `std::vector<T>` 那种零成本特化），
  也没有运算符重载、没有 RAII、没有移动语义。
- **结论**：写不了 C++ 那种"零成本抽象"的库；写业务逻辑够用。

### 4) vs Rust —— 不是替代，是"侧翼接管"

- Rust 的护城河是**编译期内存/线程安全**（所有权 + 借用检查 + `Send/Sync`），Impor 完全没有这套东西，也不打算有。
- Impor 能碰的只有 Rust 的**交付边缘**：把一个 DLL 交给 Rust 宿主调用（`host_rust.rs` 已交付，
  因本机无 `rustc` 标注"未验证"）；以及"不想上 cargo、不想背编译时间"的小工具。
- 顺带一个可比的数字：Impor 的 64 位库构建 **1.69 s**（TDM gcc 4.8 + 生成的单文件 C），产物 126 KB；
  Rust release 构建通常以十秒计、产物以 MB 计。这不是"更快更好"，只是量级不同。
- **结论**：替代 Rust 不成立；能接管的是"Rust 项目里那段不想用 Rust 写的小逻辑"。

### 5) vs Go —— 差在并发的"调度层"，不再差"有没有 channel"

- Go 的核心卖点是 goroutine + channel + 极简部署；Impor 有"极简部署"（126 KB、零依赖），
  v4.2 起也有 OS 线程、互斥锁、原子量（三端一致，8 线程 × 5000 次压测 `40000/40000`），
  v4.3 起补上 `std.channel`（有界/无界队列、`send`/`recv`/`try_recv`/`drain`）和 `std.pool`
  （常驻 worker 线程池），四端（解释器 / 转译 / gcc64 / tcc32）输出一致。
- v4.3.1 又把 channel 的等待从 `sleep(0.001)` 轮询换成**条件变量挂起**（`std.sync` 提供
  `make_lock/make_cond/wait/wait_ms/notify/notify_all`，`recv_timeout` 支持超时）：
  解释器与 gcc64 空闲时不再烧 CPU，tcc32 因旧头文件限制退化为 1 ms 轮询。
- 但**差的仍是调度层**：goroutine 是 M:N 调度、channel 阻塞时挂起栈；Impor 的线程是 1:1 OS 线程，
  没有 `select`、没有关闭广播，任务分派也不保证公平（诚实说：一个 worker 吃掉全部任务正常）。
- 另外 C 侧原子量目前用运行时锁实现（不是无锁），32 位 tcc 产物下不冒 `Interlocked*64` 的对齐风险。
- **结论**：服务端高并发（十万连接、P99）不要选 Impor；单机小工具、离线脚本、后台任务流水线、
  "一个进程里 4~8 个 worker 消化队列"可以。

### 6) vs JS/TS —— 差在异步与生态

- `async` / `await` 在 Impor 里只是**软关键字**（可当普通标识符），**没有异步执行模型**；
  事件循环、Promise、npm 那套都没有。
- **结论**：前端与 Node 服务端都不在射程内；能做的是"给 JS 项目产一个本地 DLL"。

### 7) vs Java —— 差在虚拟机与生态

- Impor 没有 JVM、没有反射框架生态、没有 Maven 级依赖管理（只有 `impor pkg` + vendor 目录）。
- **结论**：企业 Java 栈替代不了；但"避免装 JRE"的小工具场景成立。

## 四、Impor 真正领先的那一格：跨语言交付

这是它唯一能"同时压住四家一部分"的地方，而且有 CI 证据：

| 证据 | 数字 |
|---|---|
| 一份 `logic.impor` → 32 位 DLL（内置 tcc，`--cc tcc`） | 103,936 B（101.5 KB），0.22 s 构建，i386 |
| 同一份 → 64 位 DLL（`gcc -O2` 默认路径 / `--target win64`） | 131,035 B（128.0 KB）/ 1.24 s；`--target win64` 那条链接参数下 126,586 B / 1.69 s；PE `0x8664`，5 个导出符号 |
| 同一份 → Linux `.so`（`--target linux64`） | ELF64 x86-64，CI `C ABI matrix #44890796019` 五格全绿 |
| C 宿主（静态链接 / 动态加载） | rc=0，`add=5 fib=610 greet=hello, rust` |
| Python 宿主（64 位 ctypes） | rc=0 |
| Rust 宿主 | 源码已交付，**本机无 rustc，未验证** |
| `LoadLibrary→调用→FreeLibrary→退出` | 32 位 mode0–6 与 64 位探针全 rc=0（曾必崩，已修） |

## 五、不该用 Impor 的清单（比"能用"更重要）

1. 需要第三方库（HTTP 客户端、数据库驱动、图像处理）——只有 20 个标准库模块，没有公共包仓库；HTTP/图像已通过 `bindings/` 绑定系统库，但仍不是纯 Impor 生态。
2. 需要 goroutine 那类调度级并发（十万连接、`select`、可挂起栈）——有 OS 线程 + 锁 + 原子量 + channel/线程池，但没有 M:N 调度器，channel 是轮询等待。
3. 需要极致性能——解释器路径约为 CPython 的 0.17–0.21x（fib(22) 口径，见 `性能报告-v6.2.md`）；
   C 后端快但只覆盖子集（`fib(28)` 默认构建 42.0 ms，这是它拿得出手的数字）。
4. 需要模板级抽象——只有擦除式泛型（声明期约束，无单态化、无约束求解）。
5. 需要成熟 IDE 生态——有 VS Code 扩展与 LSP，但和 JetBrains/rust-analyzer 不在一个量级。
6. 需要长期多人协作的大型代码库——语言只有 4.3.0 一条线，社区规模为零。

这六条的**具体补法、工作量与验收标准**见 `docs/路线图-补四块短板.md`（第三方库 / 并发 / 模板抽象 / 工程化）。

## 六、怎么自己复跑这些数字

```powershell
py -3 tools\replacement_score.py          # 重新生成 docs/替代记分牌.md
py -3 tools\support_matrix.py             # 重新生成 docs\能力矩阵.md
py -3 Impor.py bench --gate               # 解释器 100 万循环门槛（3400 ms）
py -3 Impor.py build examples\fib.impor -o fib.exe   # 默认数值快路径
```

复跑时如果数字和上表不一致，**以你机器上的为准**；表里所有 Impor 数字都标了"本机实测"，不是承诺。
