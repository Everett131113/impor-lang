## 2. 声明语义（本次最重的修复）

### 根因

1. `Env.update_nearest` 找不到绑定时直接写当前环境，于是 `set q = 5` 成功。
2. 裸赋值在 parser 里被解析成 `scope='local'`，绕过“必须先声明”。
3. `fast_mode` 的 Python 直译把 `q = 5` 直接生成 Python 赋值，绕过树遍历。
4. `impor lint` 的 `_decl_names` 把 `update` 当成模块级预声明，静态分析也看不见。

### 修法

- `impor/interpreter.py::Env.update_nearest`：找不到绑定改为抛 `NameError`，消息为“变量 X 未声明；首次赋值请写 `var X = ...`”。
- `impor/parser.py`：裸赋值（`Var` 左值）scope 改为 `update`，不再当局部声明。
- `impor/interpreter.py::_fast_eligible`：`update/global/nonlocal` 赋值不再走 Python 直译，强制回退树遍历。
- `impor/analysis.py`：`update/global/nonlocal` 不预声明、不隐式建符号；未声明即 `undeclared-assign` error；enum 合成赋值单独豁免。
- `impor/cli.py::_decl_gate`：`run` / `build` / `compile` 在解析后、类型检查前统一跑声明门禁。
- `impor/ctrans.py`：函数参数与 `var` 局部名一起进 `_fn_writes`，修复裸赋值改 `update` 后 C 后端把参数误当全局（`game_2048.impor` 曾报 `'g5' undeclared`）。

### 实测

```text
set q = 5   → run rc=1 / lint rc=1 / build rc=2 / compile rc=2，均输出“变量 q 未声明”
w = 7       → run rc=1
z := 5      → run rc=1
var w = 1; w = 2 → run rc=0，输出 2
函数内 var w = 1; w = 2 → run rc=0，输出 2
```

全仓 206 个 `.impor` 重扫 `undeclared-assign`：**0 个文件**。

回归测试：`tests/test_strict_declarations.py`（5 条，四端覆盖）。

## 1. 同义写法：为什么没有直接删

现状（**3.13.0 当时**）：`parser.py` 仍接受 `unless`、`do..until`、`for each`、`1..5`、C 风格 `for`、`x++`、`&&/||/<>`、`:=`、`print` 省括号、`then`。v4.0.0 已把这些分支从 parser 删除。

直接删除会破坏：
- 22 个测试文件里的兼容性用例；
- `examples/snake.impor`、`game_2048.impor` 等 138 处 `++/--`。

3.13 的处理是**收敛而不破坏**：
- `impor fmt` 只输出主写法；
- `impor lint --style` 对 `style-unless`、`style-foreach`、`style-incdec`、`style-operator`、`style-walrus` 等逐条报“改用主写法”；
- 新增项目/教程/发布示例一律使用主写法；
- 兼容层标记为 **deprecated，不再是推荐写法**。

这不是“删掉十二种”，是“把十二种降级为一种主写法 + 明确的迁移提示”。**若要求物理删除，需要一次 breaking release，并同步改 22 个测试文件与全部示例**；3.13 不做这件事，避免在 50 分钟窗口里制造更大的回归。**v4.0.0 已执行这次 breaking release**：33 个测试文件 191 处、`bootstrap/imporc.impor` 55 处、9 个兼容 fixture 已迁移。

## 3. 类型注解：降级而不是伪装

`impor/typecheck.py` 只检查：
- `var x: T = 字面量`；
- 函数 `return` 的字面量。

它**不做**：赋值后追踪、流分析、泛型、运行时强制。

因此 3.13 的文档口径统一为：**类型注解是可选的静态提示，不是类型系统；运行时仍是动态语义。** 不再使用“有类型系统”“类型安全”这类表述。详见 `docs/类型注解边界.md`。

## 4. 后端分叉：改口径，不假装统一

| 能力 | 解释器 | C 后端 |
|---|---|---|
| 整数 | Python 大整数 | int64，溢出报错 |
| 自定义异常 | 支持 | 编译期拒绝（rc=3） |
| 真线程 / async | 无 | 无 |
| 发布定位 | **默认路径** | **可选路径** |

3.13 删除“C 后端是唯一发布通道”的表述，改为“解释器/便携版是默认发布路径，C 后端用于脱离 Python 分发”。两者语义分叉**明确写在规范 §23**，不再让读者以为 `build` 出来的 exe 和 `run` 完全等价。

## 5. 性能口径

`fib(28)` 同机实测（Windows x64，5 次）：

| 路径 | 稳定耗时 |
|---|---:|
| 解释器 | 301–331 ms |
| C exe | 473–479 ms |

C 后端约慢 40%–55%。原因：C 值模型是 `Val*` 装箱 + GC，递归调用比 Python 树遍历开销更大。README 已新增“算力口径”一节，并明确：**C 后端的价值是脱离 Python 分发，不是提速。**

## 7. 定位

**教学语言 + 小型工具 + 可发布玩具。**

不宣称：系统语言、生产脚本语言、比 C 快、类型安全、C 后端与解释器完全等价。

明确缺：真线程 / async、泛型、yield、默认参数、推导式、with、64 位 tcc。
