# v6.4 性能报告：换掉 tcc + 快路径扩容，产物逼平 C

> **历史内部性能报告标签，不是发布版本号。** 当前对外发布仍为 `4.0.0`；本文的 `v6.4` 只用于性能对照。

- 日期：2026-11-21
- 环境：Windows x64 / Python 3.11.5 / x86_64 gcc = TDM64 4.8.1（`C:\Program Files (x86)\Dev-Cpp\MinGW64\bin\gcc.exe`）/ 内置 tcc
- 方法：直接起进程、每种跑 7 次取最优、**含进程启动**（不经 `cmd /c`，那会多约 40 ms shell 开销）
- 目标：把 `fib(25)` 与 100 万循环压到 `< 0.07 s`，并让这个数字对**全部脚本**成立，而不只对纯整数脚本成立

## 一句话结论

`impor build` 改用 **gcc -O2** 后，同一份生成的 C：

- 数值快路径：`fib(25)` **21.5 ms**、百万循环 **20.7 ms**（手写 C 基准 19.6 / 19.2 ms，即 **1.10× / 1.08×**）
- **完整 `Val` 装箱后端：百万循环 20.0 ms**（与快路径相同）
- 浮点百万循环：**22.9 ms**

也就是说：**“装箱惩罚”不是 8 倍，而是几乎没有**——真正被 8 倍拖住的是 tcc 不会内联、不会做循环优化。这一点在本轮把结论推翻并重写（见下「被推翻的旧结论」）。

## 一、编译器选择（Tier 0）

`impor build` 新增 `--cc`，默认策略 `auto`：

| 取值 | 行为 |
|---|---|
| `auto`（默认） | 找得到 x86_64 gcc 就用 **gcc**，找不到退回内置 tcc |
| `tcc` | 强制内置 tcc（便携、产物 6.6 KB 级） |
| `gcc` / `clang` / 绝对路径 | 用指定编译器，带 `-std=gnu99`、`-O{0..3}`、`-lm` |

另可选：`-O0 / -O1 / -O2 / -O3`（等价 `--opt N`）；环境变量 `IMPOR_BUILD_CC` 可全局限定。

**同一份生成的 C，换编译器实测**（`bench_gcc_vs_tcc.py`，5 次取最优）：

| 后端 | tcc | gcc -O0 | gcc -O2 | gcc -O3 | 手写 C -O2 |
|---|---:|---:|---:|---:|---:|
| 数值快路径 `fib(25)` | 19.8 | 16.8 | **16.6** | 16.2 | 19.6 |
| 数值快路径 百万循环 | 24.2 | 19.1 | **16.1** | 16.3 | 19.2 |
| 完整 `Val` `fib(25)` | 117.2 | 40.7 | **29.1** | 20.3 | — |
| 完整 `Val` 百万循环 | 210.6 | 61.8 | **17.7** | 18.9 | — |

生成的 C 在 `gcc -O2` 下**比手写 C 基准还快**（16.6 vs 19.6），因为它的 `iadd/imul` 溢出检查被 GCC 折进了循环，而手写基准留了函数调用边界。

## 二、交付形态实测（默认 `impor build`，gcc -O2）

| 脚本 | 后端 | 体积 | 构建耗时 | 运行（含启动） |
|---|---|---:|---:|---:|
| `fib(25)` | 数值快路径 | 127.0 KB | 0.77 s | **21.5 ms** |
| 百万循环 | 数值快路径 | 127.0 KB | 0.74 s | **20.7 ms** |
| 浮点百万循环（`s + i * 0.5`） | 数值快路径（double 域） | 227.5 KB | 0.82 s | **22.9 ms** |
| 百万循环 `--no-fast` | 完整 `Val`（任意精度） | 141.5 KB | 1.28 s | **20.0 ms** |
| 参考：手写 C `-O2` | — | 约 45 KB | — | 19.6 / 19.2 ms |

体积差异全部来自静态链接运行时：同一脚本 tcc 产物 6.6 KB vs gcc 127 KB（gcc 把 libmingw/libm 静态塞进去了）。要极小产物：`--cc tcc`。

## 三、快路径扩容（Tier 1）

`impor/cfast.py`：

1. **`range` 三形态**：`range(N)`、`range(A, B)`、`range(A, B, STEP)` 全部进快路径。生成 `_impor_start/_impor_stop/_impor_step`，用三元条件做“正步长向上、负步长向下”；`STEP = 0` 是运行期错误（中文提示 + 退出码 3），不会死循环。
2. **循环后变量值修正**（本轮顺带修掉的语义 bug）：循环体开头写 `变量 = _impor_i`，于是循环结束后变量停在**最后一个值**（`range(5)` → 4），与解释器一致。patch4 时停在越界值（5），是错的。
3. **多参数 `print`**：`print("合计", s, "结束")` 按解释器“空格连接”语义一次 `printf` 输出，字符串与整数可混排。
4. **浮点 `double`**：脚本里出现浮点字面量时，整个数值域切成 `double`；变量类型用固定点推断（`_assign_map` / `_expr_ty` / `_infer_types`）。C 侧新增 `impor_dstr`（最短往返 + Python repr 风格的定点/指数切换，`-0.0`、`1e+16`、`1e-05`、`0.30000000000000004` 全部对齐）与 `impor_dmod`（浮点取模符号跟随除数）。

**明确回退（不静默改语义）**：同一变量既被赋整数又被赋浮点、浮点脚本含自定义函数、`range` 边界是浮点 —— 一律 `FastUnsupported`，由 CLI 自动落到完整后端（现在同样用 gcc，代价极小）。

对拍：`cmp_fast_vs_interp.py` 用 24 个用例比对“解释器 stdout”与“构建产物 stdout”，**OK 24 / FAIL 0**。

## 四、被推翻的旧结论（诚实记录）

上一版路线文档（`怎么让Impor速度追上C-2026-11-21.md`）写的是“完整 `Val` 装箱有 8 倍惩罚，必须实现单态化才能追上 C”。本轮实测否掉了这个判断：

- 8 倍差距出现在 **tcc** 下（117.2 / 210.6 ms），换 `gcc -O2` 后是 29.1 / **17.7 ms**。
- 交付形态（`--no-fast` + 默认 gcc）百万循环 **20.0 ms**，与快路径 20.7 ms 基本一样。
- 所以 Tier 2 的“消除装箱 / 单态化 / 接 LLVM”在**本轮收益上不成立**：主收益由“换编译器 + 让 C 代码更简单可优化”拿走，剩余 1.1–1.5× 才是类型特化能碰的部分。

Tier 2 因此交付为 **结论 + 数据 + 不实现理由**，不写一套会长期增加维护面、却只换来 1–2 ms 的单态化基础设施。

## 六、复现

```powershell

python Impor.py build cmp_fib25.impor  -o fib25.exe

1..7 | % { Measure-Command { .\loop1m.exe } | Select-Object -ExpandProperty TotalMilliseconds } | Measure-Object -Minimum
```

## 七、没有假装的地方

- 数字都是本机单轮的较好值；跨机、跨编译器的波动区间约 ±15%（同一产物连续两轮：fib 21.5–23.2 ms、loop 20.7–26.9 ms）。
- 快路径仍是 `long long` / `double` 的定宽数值：溢出报中文错误并以退出码 3 结束，任意精度请 `--no-fast`。
- 语言 lexer 本身不认 `1e16` 这类指数字面量（会解析成 `1` + 变量 `e16`），浮点请写小数形式；这是词法层既有行为，不是本轮引入。
- gcc 产物大（127 KB 起）是静态链接的代价，不是“代码膨胀”。
