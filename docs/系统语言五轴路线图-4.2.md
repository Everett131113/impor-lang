# Impor 系统语言五轴路线图（4.2 线）

> 记录时间：2026-11-22 13:50（Asia/Shanghai）
> 本文回答的问题：**Impor 能不能成为“最好的通用系统语言”**。
> 结论一句话：**能，但不是靠继续加功能，必须先换内核。**
>
> 版本口径：用户要求冻结 4.2.0；实际检查时 `VERSION` 已于 13:47 被并行进程改为 **4.3.0**。
> 本文不擅自回退版本号，也不把当前树当作已冻结基线。冻结对象需先确认。

## 1. 先钉死五条竞争轴

“最好”必须先定义成可测量、可复跑的五条轴，否则只是形容词：

1. **性能**
2. **内存 / 资源控制**
3. **并发**
4. **互操作与交付**
5. **工具链与生态**

## 2. 当前上限由内核决定，不由特性表决定

当前核心是：**Python 解释器里的动态 `Val` + 装箱 + 一个只静态翻译子集的 C 后端**。这决定了现在的天花板：

| 轴 | 当前实测 / 现状 | 为什么到不了“最好” |
| --- | --- | --- |
| 性能 | 解释器路径约为 CPython 的 **0.17–0.21×**（fib(22) 口径）；C 后端 fib(28) **42 ms** | C 后端能打，但 4.2 基线只覆盖 16 项能力中的 **14/16**（当前 4.3 矩阵为 17/19）；类型注解没有进入单态化，类型信息不参与代码生成，没有栈分配、没有去装箱 |
| 内存 | 有 GC；无裸指针、无手工释放、无确定性析构 | 只有一种内存模型，无法同时服务“随手脚本”和“峰值可预测的系统程序” |
| 并发 | 4.2 基线：1:1 OS 线程 + 锁 + 原子量，无 channel / 协程 / 线程池；当前 4.3 树已有阻塞式 `std.channel` 与 `std.pool`，但仍无 M:N 协程、无结构化取消 | 没有 M:N 调度，8 核线性扩展无从谈起；channel 是互斥锁队列 + 自旋等待，不是可挂起运行时的调度原语 |
| 互操作 / 交付 | 单文件 exe 中位 **126 KB**、启动 **33 ms**；C ABI DLL 已实测 | 目前主要出 exe / dll；没有一份源码稳定出 exe / dll / wasm / `.h` 的多目标闭环 |
| 工具链 / 生态 | 4.2 基线 **16 个标准库模块**；当前 4.3 树 **18 个**（新增 `channel` / `pool`）；无公共包仓库；VS Code + LSP | 系统语言不靠包仓库，但需要 syscall 级 std、DWARF/CodeView 调试、交叉编译矩阵、sanitizer |

> **口径漂移提醒**：当前树已被并行进程改为 **4.3.0**。`docs/能力矩阵.md` 是 19 个用例、C 后端（完整）17/19、C 后端（auto）16/19、imporc 7/19；`tools/api_baseline.json` 记录 18 个 std 模块。上表把“4.2 基线”和“当前 4.3 树”分开写，冻结后必须按实际树重跑 S6 记分牌，不能把两套数字混用。

补充两条已在代码里核实的事实，避免把“现状”说错：

- 类型注解并非“完全解析后丢弃”。`impor/typecheck.py` 已对字面量赋值、函数参数、返回值、参数个数和泛型调用做轻量门禁，`run` / `compile` / `build` 入口会中止并返回 2。
- 但这仍不是类型系统：没有流分析、容器元素类型、可空性运行时强制，也没有单态化；C 后端不会因此生成去装箱的专用代码。

## 3. 唯一可行路线：双档语言，而不是两门语言

目标成立的前提是 **script tier / system tier 双档**：

- **script tier**：保留现在的动态 `Val`、GC、随写随跑，服务脚本与交付层。
- **system tier**：由类型标注决定，进入静态类型、单态化、无装箱、栈分配、可选 `own` / `arena` / `unsafe`，服务系统程序。

这不是新发明：C# 的 safe/unsafe、D 的 `@safe/@system`、Zig 的显式 allocator 都是同一解。**一套语法覆盖两档，档位由类型标注决定**，避免维护两门语言。

## 4. 五轴记分牌：现在与“最好”的定义

下表“现状”列以 **4.2 基线** 为主；当前 4.3.0 树的漂移在括号内单独标出。冻结对象确认后，以实际树重跑的数字为准。

| 轴 | 现状（4.2 基线，括号内为 4.3 漂移） | “最好”要定义成什么 | 决定性改动 |
| --- | --- | --- | --- |
| ① 性能 | 解释器 0.17–0.21× CPython；C 后端 fib(28) 42 ms；C 后端能力 14/16（当前 17/19） | 同算法同数据结构下达到 C 的 **0.5–2×**，不是超过 C | 静态类型 + 单态化 + 无装箱 + 栈分配 + LLVM 后端 |
| ② 内存 | GC；无裸指针、无手工释放 | 三档可选：GC / arena / unsafe 手工；确定性析构；可 freestanding；峰值可打印、可复现 | 把 `Val` 一分为二：值类型 vs 引用类型；引用可标 `own` / `arena` |
| ③ 并发 | 1:1 OS 线程 + 锁 + 原子量；当前 4.3 已有阻塞式 `channel` + `pool`，仍无 M:N 协程 | M:N 协程 + channel + 结构化并发；8 核线性扩展 ≥ 0.9；可中断调度器；无运行时模式降级为“无协程” | 可挂起执行帧 + M:N 调度器 + channel |
| ④ 互操作 / 交付 | 126 KB exe / 33 ms 启动 / C ABI DLL 已实测 | 一份源码同时出 exe / dll / wasm / `.h`，ABI 版本化 | 后端多目标化（已走约 60%，补 wasm） |
| ⑤ 工具链 / 生态 | 16 个 std 模块（当前 18 个）；无包仓库；VS Code + LSP | syscall 级 std（mem/io/os/net/sync/alloc）、DWARF 调试、交叉编译矩阵、sanitizer | 系统语言生态不等于包仓库；按 C 的路走头文件 + 库 + FFI |

## 5. 执行顺序：每级不达标不进下一级

| 阶段 | 估算 | 内容 | 硬门槛 |
| --- | --- | --- | --- |
| **S1 类型系统** | 0.5–1 人年 | 注解从“轻量门禁”升级为“参与编译”；先只报错不改行为，再做单态化 | 同一份 fib 在 system tier 下无装箱、无 `Val`，性能 ≥ C 的 0.5× |
| **S2 内存分层** | 0.5–1 人年 | 保留 `defer`，补 `own` / `arena` / `unsafe` | 一个程序在 system tier 下零 GC 分配跑完，峰值内存可打印且可复现 |
| **S3 原生后端** | 1–2 人年 | LLVM 或 Cranelift；保留 tcc 快路径作为“0.13 s 构建”卖点 | 解释器 / C / 原生 / imporc 四路 conformance 逐字节一致 |
| **S4 并发** | 0.5–1 人年 | 4.3 已有阻塞式 `channel` / `pool`，S4 直接补可挂起执行帧、M:N 协程、结构化取消与“无运行时降级”；补 `yield` 生成器前置 | 8 核线性扩展 ≥ 0.9；无运行时模式可用 |
| **S5 交叉编译与调试** | 0.5 人年 | Linux/macOS/裸机目标 + DWARF/CodeView | 外部机器能构建并调试；不是只在本机可跑 |
| **S6 记分牌公开** | — | `tools/systems_score.py`：同机跑 C / Rust / Go / Zig / Impor 五列 | 任何人一条命令复跑，数字可追溯 |

合计 **3.5–6 人年**（单人全职、已有 LLVM 经验）。前提是架构一次定死，不能边做边改档位语义。

## 6. 必须公开放弃的三件事

1. **不与 C/C++ 拼绝对峰值性能**（SIMD、手工汇编、极致 cache 调优）——目标是“2× 以内且默认安全”。
2. **不与 Rust 拼编译期安全证明**——不引入所有权 / 借用检查，改用 `unsafe` 标记 + sanitizer + 运行时检查这条更便宜的路。
3. **不与 Python 拼生态广度**——不建公共包仓库，走 C 的路：头文件 + 库 + FFI。

三条不写清楚，五轴就会退化成“五轴都还行”，比现在更糟。

## 8. 对外表述边界

在 S1 门槛达成前，只能说：

- “Impor 正在评估双档系统语言路线”；
- “当前仍是交付层语言，不是可替代 C 的系统语言”。

不能说：

- “已经是系统语言”；
- “性能达到 C 的 0.5–2×”；
- “支持 wasm / 裸机 / M:N 并发”。
