# Val 表示：从 56 字节到 tagged union，以及 8 字节 NaN-boxing 的真实障碍

> 版本：4.7.2　适用：`impor/c_runtime.c`（完整后端）、`impor/ctrans.py`（内嵌运行库）、`impor/cabi.py`（FFI 包装）

## 1. 已落地：56 字节 → 16 字节 tagged union

改造前：

```c
typedef struct { VType t; long long i; double f; char *s; Arr *a; Obj *o; Fn *fn; } Val;   /* 56 B */
```

改造后：

```c
typedef struct { VType t; union { long long i; double f; char *s; Arr *a; Obj *o; Fn *fn; }; } Val;  /* 16 B */
```

依据：一个 `Val` 在任一时刻**只有一个类型**，6 个指针槽天然互斥，没必要各占 8 字节。

**这次改造踩到的唯一真坑**（已修，写在这里防止以后再踩）：旧代码大量使用「先把所有槽清零再赋目标槽」的写法：

```c
Val v; v.t = V_STR; v.i = 0; v.f = 0; v.s = strdup(s); v.a = NULL; v.o = NULL; v.fn = NULL;
```

在 7 槽结构下这是"保险"，在 union 下 `v.a = NULL` / `v.o = NULL` 会把刚写好的 `v.s` **重新清零**（同一地址）。
症状：字符串全部输出 `(null)`，但 `t` 仍然正确 —— 极容易被误判成编码问题。

修法（共 23 处构造点）：**只写 tag + 目标 payload**，其余不写。

```c
static Val v_str(const char *s) { Val v; v.t = V_STR; v.s = strdup(s ? s : ""); return v; }
```

生产端唯一不变式：**构造只写一个 payload 槽**。

## 2. 为什么没直接上 8 字节

### 2.1 访问面规模（`tools/count_val_access.py` 实测）

| 文件 | 访问点 | 写 | 读 |
| --- | --- | --- | --- |
| `c_runtime.c` | 620 | 52 | 568 |
| `ctrans.py`（内嵌 C） | 255 | 23 | 232 |
| `cabi.py`（生成 C） | 20 | 0 | 20 |
| **合计** | **895** | **75** | **820** |

字段分布（全局合计，去掉注释后统计）：t=270 / i=74 / f=27 / s=175 / a=304 / o=30 / fn=15。

> 口径以 `tools/count_val_access.py` 的输出为准。早先一次同类统计报过 915，差异来自注释剔除与
> 正则边界（`v.t` 出现在字符串/注释里会被旧口径计入），这里统一用脚本可复现的 895。

8 字节意味着 `Val` 变成 `uint64_t`，`.t` / `.i` / `.f` / `.s` / `.a` / `.o` / `.fn` 这些**字段语法全部失效**，
820 个读点要改成访问器调用，75 个写点要改成 setter（`v.i = x` 不再可能），并且要避开 `RtStrNode.s` / `RtBuf.s`
这类同名冲突（先重命名）。

### 2.2 真正的硬障碍：int64 全范围与 64 位载荷冲突

NaN-boxing 的经典编码依赖"double 的 NaN 空间装指针/小整数"，因为 double 的 64 位里有一大段是不会被正常数值使用的。
但 Impor 的整数语义是 **int64 全范围**（`-9223372036854775808 ~ 9223372036854775807`，越界报 E1012），
int64 的 2^64 种位模式里**每一种都对应一个合法整数**，没有空闲位放 tag。

于是只有三条路，每条都要付代价：

| 方案 | tag 位置 | 代价 |
| --- | --- | --- |
| A. 整数只用 48/60 位，超出转 boxed | 低位对齐 tag | `|x| > 2^47` 的整数要堆分配 → 长整数运算退化，E1012 边界仍要对齐 |
| B. 所有整数都 boxed，Val 只装指针/double/小标量 | 低位 tag | 每个整数一次 malloc，1e8 循环直接不可用（除非整段特化，而特化已经把整数剥离出 Val） |
| C. 指针左移 + 低位 tag，double 原样，整数另立通道 | 低位 3 位 | 需要"整数值不可能是 double 位模式"的假设，与 Impor 的 `1 + 1.0` 混合语义冲突 |

**结论**：8 字节在"int64 全范围 + double 同构"的语义下不是免费午餐。若要上，必须先在语言层
定义"整数是否允许 boxed 化"，这属于语义决策，不是纯后端重构。

### 2.3 已获得的部分收益

- `sizeof(Val)`: **56 → 16**（-71%）。`Arr` 的元素数组、栈帧里的临时 Val 同步缩小。
- 16 字节正好是两个 8 字节寄存器，gcc 用 SSE 一次搬移，结构体传参不再走内存。
- 访问 `.t` / `.i` 的代码**一字未改**（匿名 union），所以 895 个访问点全部保持，回归风险为零。

## 3. 如果要做 8 字节，建议的落地顺序

1. **前置**：`RtStrNode.s` / `RtBuf.s` 重命名为 `.str`，让 `.s` 全局唯一属于 Val（约 40 处）。
2. **访问器层**：用 `tools/count_val_access.py` 生成替换清单，先引入
   `#define VT(v) ...` / `VI(v)` / `VF(v)` / `VS(v)` / `VA(v)` / `VO(v)` / `VFN(v)`，
   在**16 字节结构**上先让 820 个读点全部走访问器（此时结构不变，行为不变，可全回归验证）。
3. **写点**：75 处 `X.f = ...` → `V_SET_F(&X, ...)`；这一步最危险，因为要区分 `X` 是左值变量还是指针解引用。
4. **切换表示**：把访问器实现从"读结构体字段"改为"位运算解码"，`Val` typedef 改成 `uint64_t`，一次编译暴露所有漏网。
5. **语义决策**：确定整数的 boxed 阈值（方案 A/B/C 三选一），E1012 边界与解释器对齐。
6. **回归**：277 个 `.impor` + 23 项 parity + conformance 425s。

第 2 步可以独立先做、独立验证，是这条路上唯一"零风险前进"的一步。
