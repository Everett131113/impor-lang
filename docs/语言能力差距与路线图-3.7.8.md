# Impor 语言能力差距与路线图（v3.7.8）

> **历史文档（v3.7.8，2026-11 归档）**：本文中的能力表不代表 3.13.0。当前边界以 `docs/3.13-后端能力边界.md` 与 `docs/语言规范.md` §23 为准；两者冲突时，以 3.13 文档为准。

本文回答三个问题：Impor 还能怎么改语法、编辑器还能怎么做大更新、相对 C / Python 还缺什么。  
原则：**所有方向都开始，但每个方向只把能验证的第一块写进版本**；未完成项继续列出，不冒充完成。

## 1. 当前基线

- 解释器：完整语法，支持模块、类、异常、管道、async/await、match、ADT。
- Python 转译：`impor compile`，产物依赖 `impor.runtime`。
- C 后端：`impor build`，AST → C → tcc → 独立 exe；值模型为 `Val`。
- 自举编译器：`imporc` 仍是 v3.3 语法子集，宽容写法与新增语法不走它。
- 编辑器：Tk 多编辑组、LSP 六项、DAP 条件/异常断点、大文件分块、AI 内联助手、Git 审查台、插件隔离。

## 2. 相对 C 的硬缺口

| 缺口 | 现状 | 影响 | 优先级 |
|---|---|---|---|
| 异常与确定性清理 | 解释器有 `try/catch/finally`；C 后端不支持 `try/catch`、自定义异常；`defer` 只在新解释器/转译 | 无法写可靠的资源清理与错误恢复 | P0 |
| 库化与 ABI | 只产出 exe，不能导出 `.dll/.a`，不能解析 C 头文件；FFI 白名单只覆盖 int/float/str/bool | 不能被其他语言调用，也难复用现有 C 库 | P0 |
| 内存与布局 | 无指针、union、bitfield、packed struct；`struct` 是 class 脱糖 | 不能做系统编程、硬件寄存器、二进制协议 | P1 |
| 并发 | `async/await` 是单线程任务；无真线程、原子、channel | 不能写并发服务/并行计算 | P1 |
| 优化与调试 | 只有 tcc，无 LLVM、DWARF、跨平台原生构建；`--fast` 只覆盖纯整数子集 | 性能与调试体验受限 | P2 |
| 标准库落地 | 文件、网络、TLS、SQL 仍偏宿主能力 | 真实服务需要自己搭轮子 | P2 |

**结论**：C 后端现在是“能出独立 exe 的快速运行产物”，不是“可替代 C 的系统语言”。要往真实工具/服务走，先补 P0：统一清理语义 → 库导出/头文件 FFI → 线程与原子。

## 3. 相对 Python 的硬缺口

| 缺口 | 现状 | 影响 |
|---|---|---|
| 资源管理 | 无 `with`；`defer` v3.7.8 已有 | 文件/锁/事务缺少统一协议 |
| 生成器 | 无 `yield` | 不能惰性序列、流式处理 |
| 函数签名 | 无默认参数、`*args`、`**kwargs`、参数解包 | API 设计受限，包装器难写 |
| 推导式 | 无 list/dict/set 推导式 | 集合处理样板代码多 |
| 结构化模式 | 只有字面量/绑定/通配 + ADT 模式；无序列、映射、类模式与 guard | 复杂数据解构弱 |
| 类型系统 | 注解只解析后丢弃，不检查，无泛型 | 大项目缺少静态保障 |
| 装饰器 | 无 | 横切关注点（日志/缓存/权限）难复用 |
| 生态 | 私有源，无 PyPI 规模，无 C 扩展 ABI | 第三方库少 |

**结论**：若要“教学与表达力”，先补 `with/defer`、默认参数与变参、`yield`、推导式；若要“工程能力”，先补类型检查与包生态。两者不能同时全速推进。

## 4. 四端不一致（比“缺功能”更急）

| 能力 | 解释器 | Python 转译 | C 后端 | imporc |
|---|---|---|---|---|
| 管道 `\|>` | ✅ | ✅ | ✅ v3.7.8 | ❌ |
| `try/catch`、自定义异常 | ✅ | ✅ | ❌ | 部分 |
| `defer` | ✅ v3.7.8 | ✅ v3.7.8 | ❌ 明确拒绝 | ❌ |
| 嵌套类 | ✅ | ✅ | ❌ | ❌ |
| 两层以上嵌套函数/自递归闭包 | ✅ | ✅ | ❌ | ❌ |
| 宽容写法（`unless/then/of/:=/->` 等） | ✅ | ✅ | 部分 | ❌ |

处理原则：
1. 新语法先定“四端支持 / 明确拒绝”，不允许静默丢语义。
2. C 后端与 imporc 的拒绝必须是编译期友好报错，不能生成错误产物。
3. 文档只写实现真实支持的能力；`docs/语言规范.md` 已修正 C 后端 `try/catch/finally` 的错误表述。

## 5. 语法还能怎么改

已有大量同义写法（`unless`、`then`、`of`、`:=`、`->`、C 风格 `for`、`do-until`、`..` 闭区间），继续加别名边际收益低。优先做结构性语法：

| 候选项 | 价值 | 风险 | 建议 |
|---|---|---|---|
| 解构遍历 `for i, v in arr` / `for k, v in dict` | 高 | 中，改 for 绑定 | v3.7.9 第一块 |
| 半开区间 `0..<n` | 中 | 低 | v3.7.9 |
| `guard cond else { ... }` 早退 | 高 | 中，改控制流 | v3.7.9 |
| 命名参数与默认值 | 高 | 高，动函数调用绑定 | 单独立项 |
| `defer` → `with` | 高 | 中，需资源协议 | v3.7.9 |
| `yield` | 中 | 高，需生成器/状态机 | v3.8 后 |
| 推导式 | 中 | 中，需新 AST 与作用域 | v3.8 后 |
| 类型检查/泛型 | 高 | 很高，动全链路 | 单独立项 |

## 6. 编辑器还能怎么做“大更新”

已有多编辑组、行内诊断 + F8、Git 审查台、可配置键位、测试耗时/覆盖列、大文件分块、AI 内联、DAP、LSP 六项、统一分析、命令面板、UIA、设置同步、插件隔离。继续加小功能不如选一条路线：

| 路线 | 内容 | 代价 | 建议 |
|---|---|---|---|
| A. 编辑器内核 3.0 | Tk Text → Monaco/WebView2 或 Qt+Scintilla；多光标、折叠、minimap、平滑滚动、内联 diff、hover 卡片、更好 IME | 重写编辑面板并重适配 UIA/插件/调试/大文件，2–3 个版本 | 先做 PoC，不伪装成普通版本 |
| B. 工作区 2.0 | 多根工作区、项目树、workspace trust、每项目配置、项目级符号索引、搜索范围、会话恢复、布局保存 | 风险最低，一个版本可交付 | v3.8 主更新 |
| C. AI 工作台 2.0 | 逐 hunk 接受/拒绝、多文件补丁事务与回滚、项目索引上下文、本地 endpoint、硬超时取消 | 中，依赖 AI 层重构 | v3.9 |

**建议**：v3.8 做 B（工作区 2.0），A 只做 PoC，C 放 v3.9。A 是架构级质变，应该单独说明，不应混在普通迭代里。
