# v6.7 性能报告：`impor serve` 常驻（P2）+ 完整 C 后端接管（P3）

> **历史内部性能报告标签，不是发布版本号。** 对外发布仍为 `4.0.0`；`v6.7` 只用于性能对照。

- 日期：2026-11-21
- 计法：自写 `hbench.exe`（`CreateProcess` + `WaitForSingleObject` + `QueryPerformanceCounter`，10 次取最优）。**不用 PowerShell 的 `&` 直测**，那会多算 15–20 ms 的管道开销。serve 的「每请求」由 `impor-serve-client.exe -n N` 在**同一条 TCP 连接**上连发 N 次后报均值——这是真实用户在编辑器里连续跑的形态，不是冷启动。
- 本机：Windows x64；Python 3.11.5（`D:\编程软件\python3.11\python.exe`）；gcc 4.8.1（TDM64，`-std=gnu99`，x64）。
- 基准脚本：`cmp_loop1m.impor`（`for i in range(1000000)` 累加）、`cmp_fib25.impor`（朴素 `fib(25)`，24 万次调用）、`g1.impor`（字符串 + 列表 + `len` + 函数 + 递归 + `print`，输出 `hi Impor 3 499999500000`）。

## 结论先摆

| 路径 | 100 万循环 | `fib(25)` | 字符串/列表/函数脚本 `g1` | 形态 |
|---|---:|---:|---:|---|
| C（gcc -O2，手写基准） | 16.5 ms | 16.7 ms | — | 物理下限 |
| `impor build` 产物 | 16.9 ms | 16.3 ms | — | 一次性编译 |
| `noop.exe`（空进程） | 16.9 ms | 16.9 ms | 16.9 ms | **进程创建地板** |
| **启动器 `impor-fast.exe`（P1/P3）** | **25.6 ms** | **25.7 ms** | **31.6 ms** | 每跑一次 = 一个新进程 |
| **`impor serve` 每请求（P2/P3）** | **4.79 ms** | — | **75.7 ms** | 常驻，零进程创建 |
| `impor run`（P0 默认原生） | 214.0 ms | 231.4 ms | 230.3 ms | 每次都起 Python |
| `impor run --no-native`（纯解释器） | 2132.4 ms | 187.1 ms | **8879 ms** | P3 的主要反例 |

三句话说完：

1. **P2 落地了，而且比 patch7 预估的还好。** 百万循环从启动器的 25.6 ms 压到 **4.79 ms/请求**——已经低于 C 的 16.5 ms，因为 C 那个数里含着 16.9 ms 的进程创建，而常驻服务把这笔一次性成本摊成了 0。这不是「语言比 C 快」，是**形态差异**：同一个产物，一个每次新起进程，一个住在常驻进程里。
2. **P3 让完整 C 后端接管了 `run` 与启动器的回落档。** 字符串/列表/函数/异常脚本不再回落解释器：`g1` 走完整 C 后端后，`run` 口径 **8879 → 230 ms**（≈38×），启动器口径 **31.6 ms**。完整后端 24 例对拍 **24/24**（含浮点 `%` 与 `repr`）。
3. **serve 的完整后端档一开始是个坑：726–749 ms/请求。** 根因不是缓存失效，是 Windows 的**控制台分配**（详见下一节）。修完 **75.7 ms/请求**，约 10×。这个坑值得单独写，因为它只在你把服务做成「脱离控制台的后台进程」时才会出现。

## P2：`impor serve` 常驻

做了什么（`impor/serve.py`，新增 227 行；`impor/cli.py` 加 `cmd_serve`）：

- `impor serve start [--bg] [--port N]` / `stop` / `status` / `run <脚本>`：state 落在 `~/.impor/serve.json`（端口 + pid），`--bg` 用 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` 起，脱离终端。
- 协议极简：客户端连 `127.0.0.1:<port>`，发一行 JSON `{"script": ..., "args": [...], "opt": 2}`，服务回一行 JSON（`code / out / err / tier / ms`）。一条连接可以连发多次请求——`-n N` 就是这样测「每次请求」的。
- **三档执行**，按可用性依次回退，响应里用 `tier` 标明走了哪一档：
  1. `dll`：数值快路径产物以 DLL 形式 `LoadLibrary` 在本进程内调用（`impor_entry(const char *out_path)`，入口里 `freopen(out_path,"w",stdout)` 把输出落到临时文件，宿主按路径读回）。
  2. `full`：完整 C 后端编译出的 exe，`subprocess` 跑一次（字符串/列表/函数/异常脚本走这里）。
  3. `interp`：进程内 `Interpreter(fast_mode=True)`，兜底。
- 首次请求不是替整个服务付 import 的钱：`serve()` 起来就 `import impor.cli / interpreter.parse_source`。

### 每请求实测

| 档 | 脚本 | 每请求 | 说明 |
|---|---|---:|---|
| `dll` | `cmp_loop1m.impor` | **4.79 ms**（19 次均值） | 低于 `noop.exe` 的 16.9 ms，因为不起进程 |
| `full` | `g1.impor` | **75.7 ms**（9 次均值） | 起一次产物进程；修复前 726–749 ms |

进程内直接调 `serve.execute()`（同机、同进程连跑）是 27–30 ms：`tier=full`、`code=0`、输出 `hi Impor 3 499999500000`。也就是说 75.7 ms 里有约 45–48 ms 是「常驻进程 spawn 一个子进程」的开销，剩下的才是脚本本身。

### 为什么会是 726 ms：Windows 控制台分配

现象：守护进程回答 `tier=full`，但每请求 690–870 ms；`~/.impor/run-cache` 里一度积了近千个 exe，看着像「缓存键每次都变、每次都重编译」。

排查顺序与结论：

1. 读 `_native_cache_key`（`impor/cli.py:337`）：键 = `sha256(abspath|src|opt|"run-native"|backend| cfast.py:size:mtime | ctrans.py:… | c_runtime.c:… | cli.py:… | v<版本>)[:24]`，**不含时间、随机量、pid**。键是稳定的。
2. 真守护进程探针：发 3 次请求，`tier=full`、690.97 / 867.57 / 801.47 ms；同时**比对 `run-cache` 前后的文件清单：新增 0 个文件**——没有重编译，缓存在命中。
3. 直接跑那份缓存产物（`hbench` 3 次）：27.4 ms。产物本身没问题。
4. 进程内调 `execute()`：27.9–29.6 ms。同一份代码，同一条路径，快 25 倍。
5. 剩下唯一的变量是**父进程的形态**。做对照实验：让一个 `DETACHED_PROCESS`（无控制台）的 Python 去 `subprocess.run` 那个 exe——
   - 不带 flags：**643.1 / 763.5 ms**
   - 带 `CREATE_NO_WINDOW`：**68.1 / 64.2 ms**

根因清楚了：父进程没有控制台时，spawn 一个控制台子系统程序会让 Windows 为它**新建一个 ConHost**，实测每次 640–760 ms。这不是 Impor 的开销，是 Win32 的开销，但它确实被算在了「每请求」里。

修法（`impor/serve.py` 的 `full` 档）：`subprocess.run(..., creationflags=0x08000000)`（`CREATE_NO_WINDOW`）。修完 75.7 ms/请求，约 **10×**。

顺带说清那个「近千个 exe」的错觉：那是本轮反复改 `c_runtime.c` / `cli.py` 导致键变化后，每轮门禁重编留下的历史产物（键里含四个工具链源文件的 size/mtime，这是设计如此——改运行库就该重新编译）。它不解释 726 ms，问题在别处。

## P3：完整 C 后端接管回落档

### 为什么不是「重写 C 内核」

用户原话是「重写 C 内核」，但实测把这件事否掉了：手写一个 C 字节码 VM 跑百万循环要 **17.2 ms**，而 `cfast` 编译产物只要 **0.3 ms**——慢 60 倍。做第二个 VM 没有收益。

所以 P3 的落点是：**复用已有的 `ctrans` 完整 Val 后端**（本来只服务 `build --no-fast`），把它接进 `run` 与启动器的回落链路。它已经能承载字符串、列表、`len`、函数、递归、异常，缺的只是「被默认路径用到」。

改动：

- `impor/cli.py`：`_native_cache_key(..., backend="fast")` 加后端维度（快路径产物与完整后端产物不能互相冒充）；新增 `_transpile_for_native`（`fast` → `cfast`，`full` → `ctrans.c_transpile(..., emit_main=True)`）、`_native_dll`（`lib=True, strip=True`，内置 tcc 返回 `None`）、`_native_product(backend)`、`_native_run` 三档链（cfast → ctrans → `None` 交解释器）。
- `impor/cfast.py`：DLL 入口签名改 `int impor_entry(const char *out_path)`，首个语句 `freopen(out_path,"w",stdout)`——跨 CRT 时 `os.dup2` 重定向在 DLL 自己的 CRT 里不生效，这是唯一可靠的做法。
- `tools/impor-fast.c`：加 ④b（完整后端 exe）与 ④c（已有完整产物 overlay）两档，`VER_STR=4.0.0p8`。

### 语义修复（P3 期间抓到的两个真缺陷）

1. **`range` 步长为 0 在完整后端是死循环**。加校验：步长 0 直接 `exit(1)` 并给出诊断。
2. **循环变量遮蔽**：`for i in range(...)` 在 for 头部声明会遮蔽同名变量，循环后 `print(i)` 打 `None`，影响 c01/c02/c03/c04/c07/c08/c09/c10 八个用例。重写为「三界（起点/终点/步长）先各求值一次存 `_ri/_re/_rs`，`for (; cond; _ri = _ri + _rs)`，循环体开头 `varc = _ri`」——与 `cfast` patch4 的做法一致。

这两处把对拍从 **13/24** 拉到 **22/24**。

### 浮点打印：从 22/24 到 24/24

剩两个用例：

- `c25_float_mod`：Python 的浮点 `%` 结果符号跟随除数，C `fmod` 跟随被除数 → 新增 `rt_fmod_py(a,b)`（`r=fmod(a,b)`；`r!=0 && (r<0)!=(b<0)` → `r+=b`），`V_FLOAT %` 改走它。
- `c30_float_repr`：`%.12g` 把 `0.1+0.2` 打成 `0.3`、`1e16` 打成 `1e+016`。换成最短往返表示。

最短往返的实现踩了三个**环境坑**，每个都值得记：

1. **不能用 `%.*f` 出定点结果**——MSVCRT 的 `%f` 末位会错（`-698301.6521509961` 打成 `…962`）。
2. **不能用 `powl` / long double**——本机 MinGW TDM 4.8.1 没有 `powl` 实现（隐式声明，调用拿到 `3.2e-317` 垃圾值），long double 在 `-O2` 下也不可靠。
3. **不能用 `%.0e` 取数量级**——它先舍入到 1 位（`952510.2` → `1e+006`，数量级多一位）。另外 tcc 的 win32 运行库**没有 `strtoll`**。

最终实现（`impor/c_runtime.c` 的 `rt_fmt_double`，并同步进 `impor/ctrans.py` 内嵌副本）：一次 `snprintf("%.20e")` 取 21 位（前 17 位准，后几位当保护位）→ 解析出 digits + exp10 → 对 p=1..17 在十进制串上做第 p 位四舍五入 → 组 `d.ddde±XX` 候选串用 `strtod` 校验能否还原同一个 double → 第一个能还原的 p 即最短位数 → 去尾部多余 0 → 按 Python 规则决定记法（`exp10 < -4 || >= 16` 走科学记数、指数至少两位；否则定点、去尾零但至少留一位小数、整数补 `.0`）。`d==0` 单独处理带符号零，NaN 打 `nan`。

#### 代价：产物变大，承诺跟着改

`strtod` 因被 `rt_fmt_double` 引用而变得可达，静态链接多约 100 KB：`hello.impor` 产物 **153,088 B → 255,488 B**。因此 vitals 里「exe ≤ 160 KB」这条承诺不再成立，本轮同步改为 **≤ 320 KB**（`docs/claims.yaml` 与 `tools/verify_release.py` 同改，文案注明「patch8 起：完整 Val 运行库含浮点 repr，静态链接 `strtod` 约 +100 KB」）。**这是对外口径变更，写在这里以便追溯**——降不下来就如实改数，而不是留着一条已经假的承诺。

#### 诚实边界

- 24 例对拍 **24/24** 全过（含 `c25_float_mod`、`c30_float_repr`、`c31_float_neg`）。
- 随机浮点 fuzz 324 例里仍有约 **5 例末位不同**：两串都能 round-trip 到同一个 double，属**显示层**差异（最后一位十进制）。要精确十进制请用 `str()` / 显式格式化，不要依赖 `print` 的默认 repr。

### 一个必须挡住的回归：`use std.*` 脚本

把完整后端设为 `run` 默认后，`conformance/compat_3_11/demo_19_split_join.impor`（`use std.text` + `split/join`）在完整后端里报 `AttributeError: 字符串无此方法 [E1006]`（解释器跑是对的）。`compat_20` 因此从 22/22 掉到 20/22。

修法：`_native_run` 里加 `_has_module_import(ast)` 门——AST 中出现 `ImportNode` / `FromImportNode` 就跳过完整后端、直接回落解释器（与 patch7 行为一致）。只让不 import 的本地脚本进 `ctrans`。修后 `demo_19` 走解释器输出正确，`g1` 仍走完整后端。

## 与其它语言同一口径的位置

本节的跨语言数字是**同机、同一计时器（hbench，10 次取最优）当轮实测**，不是旧轮次沿用：

| 语言 / 路径 | 100 万循环 | `fib(25)` | 空脚本地板 |
|---|---:|---:|---:|
| C（gcc 4.8.1 -O2，编译产物） | 18.5 ms | 17.9 ms | 19.2 ms（`noop.exe`） |
| **Impor 构建产物（gcc -O2）** | **18.3 ms** | **19.3 ms** | — |
| Lua 5.4 | 21.8 ms | 31.6 ms | 23.4 ms |
| **Impor 启动器（patch8）** | **25.2 ms** | **23.6 ms** | — |
| **Impor 常驻 `serve`（每请求）** | **4.52 ms** | **11.94 ms** | 0（无进程创建） |
| Node（本机沙箱运行时） | 123.7 ms | 134.4 ms | 117.4 ms |
| `impor run`（默认原生） | 216.1 ms | 235.5 ms | — |
| Python 3.11.5 | 233.1 ms | 130.6 ms | 93.5 ms |
| Impor 解释器（`run --no-native`） | 2112.8 ms | 232.1 ms | ≈93.5 ms |

净计算（扣各自启动地板）：C 与 Impor 产物都 ≈0（循环）/0.2–0.4 ms（递归）；Lua ≈0–2 / 10 ms；Node ≈6 / 17 ms；Python ≈140 / 37 ms；Impor 解释器 ≈2019 / 138 ms；serve 的 4.52 ms 里循环本身 0.3 ms、`fib` 的 11.94 ms 里递归 7.7 ms，其余是 IPC。

按这张表：**编译产物这一档 Impor 与 C 并列**（循环 18.3 vs 18.5、递归 19.3 vs 17.9，差值都在噪声内，净计算都在 0.5 ms 内）；启动器排第三（落后 C 系 5–6 ms，全是进程创建地板与 DLL 加载），`fib` 上比 Lua 快 8 ms；`impor run` 落在 Python 同一档（216 / 235，成本是「Python 启动 + CLI 导入」约 174 ms + 产物进程 18 ms）；解释器垫底，比 Python 慢约 9×（循环）/1.8×（递归）。

**别把 serve 的 4.52 ms 与 C 的 18.5 ms 混着说**：

- 同一形态（每跑一次新起进程）＝启动器 25.2 ms vs C 18.5 ms，差的 6.7 ms 是进程创建与加载。
- 把固定成本摊掉之后（serve）＝循环 0.3 ms，这才是和 C 净计算 0.3 ms 可比的数。
- Ling 本机无可执行文件，无法同口径复测；旧表的 Ling 数字（PowerShell 直测）不入本表，仅作历史记录。

## 边界（诚实标注）

- serve 的 `dll` 档只覆盖数值快路径能编的脚本；字符串/列表/函数脚本走 `full` 档（75.7 ms，含一次产物进程创建）。要把 `full` 档也做到个位数毫秒，得让 `ctrans` 也支持 DLL 入口——本轮没做。
- serve 的 `full` 档每请求 spawn 一个子进程，是无控制台父进程下 Win32 的真实成本（`CREATE_NO_WINDOW` 后 64–75 ms）。想再往下只有把 `full` 档变成 DLL / 进程内执行。
- 常驻不改变语义：`tier` 明确写在响应里，`use std.*` 脚本仍回落解释器。
- `run` 的 214.0 / 231.4 / 230.3 ms 主要成分是 `python -S -I` 启动 + `import impor.cli`（约 174 ms 地板），不是语言本身；同机不同负载下这条会在 185–231 ms 之间浮动。
- 浮点 repr 的 5/324 末位差异是显示层，不是算错——两个串 round-trip 到同一个 double。
- 完整后端仍不覆盖 `import`；覆盖范围以 `docs/能力矩阵.md` 与 24 例对拍为准，不夸大。
- exe 体积承诺已从 160 KB 调到 320 KB（`strtod` 静态链接 +100 KB），属口径变更，理由见上。
