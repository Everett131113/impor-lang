# 4.9.2：`have` 高亮修复说明

## 1. 问题是什么

`have` 在 4.9.1 里被做成**软关键字**：

- `impor/lexer.py` 的 `SOFT_KEYWORDS` 里有它，所以 `x have int` 能被 parser 认出来；
- 但它**不在 `KEYWORDS`** 里，所以 `var have = 1` 仍然可以当普通标识符用（`tests/test_v491.py::test_have_is_soft_keyword` 钉住了这条）。

问题出在着色器：Tk 编辑器、Qt 高亮、LSP 语义着色都只判断 `word in KEYWORDS`。
`have` 不在这个集合里 → 渲染成普通标识符色，看起来就像个变量名。

## 2. 怎么改的

新增一个「视觉关键字」集合，和语法层的关键字集合分开：

```python
# impor/lexer.py
HIGHLIGHT_KEYWORDS = frozenset(KEYWORDS | IMPLEMENTED_SOFT_KEYWORDS)   # 59 词
```

`IMPLEMENTED_SOFT_KEYWORDS` 本来就表示「有真实语义的软关键字」，4.9.1 把 `have` 加进去了，
所以着色器只要改用 `HIGHLIGHT_KEYWORDS` 就自动带上 `have` / `static` / `readonly` / `this`，
`KEYWORDS` 保持 55 不动 —— API 基线、`test_v372` 的关键字审计都不受影响。

四条着色路径：

| 文件 | 位置 | 改动 |
|---|---|---|
| `impor/lexer.py` | `HIGHLIGHT_KEYWORDS` | 新增集合（`KEYWORDS` ∪ `IMPLEMENTED_SOFT_KEYWORDS`） |
| `impor/editor_pane.py` | `highlight()` 判定 + `_symbols()` 补全 | `word in KEYWORDS` → `word in HIGHLIGHT_KEYWORDS`；并显式 `from .lexer import HIGHLIGHT_KEYWORDS`（不再单靠 `editor.py` 末尾的命名空间注入） |
| `impor/editor.py` | 顶部 import | 一并导入 `HIGHLIGHT_KEYWORDS`，随 `_split_ns` 注入到分模块 |
| `impor/kernel3.py` | `ImporHighlighter.__init__` | 关键字正则改为基于 `HIGHLIGHT_KEYWORDS`，并显式列 `have` |
| `impor/lsp.py` | `semanticTokens` + 补全 | 语义 token 判定改用 `HIGHLIGHT_KEYWORDS`；补全列表加 `have` |
| `vscode-impor/syntaxes/impor.tmLanguage.json` | `repository.keywords` | 新增一条 `keyword.operator.type.impor`，`match: "\\b(have)\\b"` |

Tk 里 `have` 拿到的是 `kw` 标签（和 `var` / `def` 同一个颜色）；`if` 之类流程词仍是 `kw2`。
VS Code 里 `have` 走 `keyword.operator.type` 这个 scope，颜色和 `if` 不同，一眼能分辨。

## 4. 边界（如实列出）

- `have` 依然是**软关键字**：`var have = 1` 合法。因此高亮是「按词形着色」，
  如果有人真的拿 `have` 当变量名，它也会被染成关键字色 —— 与 `static` / `this` 的现有行为一致。
- 没有改 `KEYWORDS`（55 不变），所以任何依赖「55 关键字」的门禁与文档都不需要动。
- 本轮只动着色与补全，**没有改动运行期语义、C 后端、WASM 后端**。
