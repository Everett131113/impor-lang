# v6.5 性能报告：`impor run` 的 C 级路径（原生启动器 + 透明编译）

> **历史内部性能报告标签，不是发布版本号。** 对外发布仍为 `4.0.0`；`v6.5` 只用于性能对照。

- 日期：2026-11-21
- 计法：自写 `hbench.exe`（CreateProcess + WaitForSingleObject，QueryPerformanceCounter，7 次取最优），**不含 PowerShell 自身的管道开销**
- 目标：让 `impor run`（开发期路径，此前 176.8 / 2061.0 ms）追上 C（16.7 / 16.5 ms）

## 结论先摆：解释器本体追不上，能追上的是“run 这条命令”

| 路径 | `fib(25)` | 100 万循环 | 相对 C |
|---|---:|---:|---:|
| C（gcc -O2） | 16.7 ms | 16.5 ms | 1.0× |
| Impor 构建产物（`impor build`，gcc -O2） | **16.3 ms** | **16.9 ms** | **1.02×** |
| `impor <脚本>`（原生启动器 `impor-fast.exe`，热执行） | **38.1 ms** | **39.7 ms** | 2.3× / 2.4× |
| `impor run --native <脚本>`（Python 入口 + 透明编译） | 317.2 ms | 305.1 ms | 19× / 18× |
| `impor run <脚本>`（AST 解释器，原状） | 176.8 ms | 2061.0 ms | 10.6× / 125× |

三句话：

1. **纯 Python 的 AST 解释器有物理地板**：`python -S -I` 空启动 39 ms、导入 `impor.cli` 197 ms，`impor run` 跑空脚本都要 186 ms。也就是说 fib 的 176.8 ms 里几乎全是启动，100 万循环那 2061 ms 才是真正的解释成本。**改造解释器内部不可能把 2061 ms 拉到 16 ms**——CPU 里跑的是 CPython 的对象和字节码。
2. **能到 C 量级的是“产物”**：`impor build` 出来的 exe 是 16.3 / 16.9 ms，和 C 的 16.7 / 16.5 ms 互有胜负，差在噪声里。
3. **`impor run` 这条命令能做到 38–40 ms**：原生启动器先看缓存，命中就直接把进程换成编译好的 exe（`_wspawnv(_P_OVERLAY)`，不再起第二个 Python）。仍比 C 多约 22 ms，那是“启动器自身进程 + 目标 exe 进程”两次进程创建的固定成本。

## 本轮做了什么

| 改动 | 作用 |
|---|---|
| `impor run --native [--cc gcc|tcc] [-O0..-O3]` | 命令、门禁、错误信息都不变；能静态编译的脚本先编译再执行，产物按“源码 + 工具链指纹”缓存；子集外脚本自动回落解释器并提示 |
| `impor build --quiet` | 只产出文件、不打印构建摘要（给启动器调用，避免污染程序输出） |
| `tools/impor-fast.c → impor-fast.exe`（新增，21 KB） | 原生启动器：`impor.bat` 早已预留这个入口；命中缓存则 overlay 执行，未命中则静默编译（`build --quiet`）后执行，编译失败回落 `run` 解释器 |
| `impor.bat` | 传 `IMPOR_CALLER_CWD`，保证相对脚本路径按“调用者目录”解析（启动器会 cd 到安装目录） |

启动器缓存：`%USERPROFILE%\.impor\fast-cache\<FNV64>.exe`；键包含脚本内容、脚本 mtime/size、`impor/cfast.py` / `ctrans.py` / `c_runtime.c` / `cli.py` 的 mtime/size 与版本串——改脚本或改转译器都会换键，不会命中旧产物。

## 为什么还差 2.4 倍（诚实的账）

`impor-fast.exe` 的一次热执行包含两次进程创建：

```
hbench → impor-fast.exe（读脚本、算键、查缓存 ~3 ms）→ overlay → 缓存的 exe（16–17 ms）
```

单独测这条 stub 的壳内耗时是 **2.9 ms**（用 QueryPerformanceCounter 打印过），剩下的差额是 Windows 的进程创建/映像加载本身。要再往下压只有一条路：**把脚本编译成 DLL，在启动器进程里 LoadLibrary 直接调用**（单进程、省掉一次加载），预计能到 18–22 ms；那需要给 C 后端加“DLL + 导出入口”模式和更细的运行时初始化控制，属于下一阶段，不在本轮。

## 回归与门禁

- 新增 `tests/test_v42_native_run.py`（4 项）：`--quiet` 不打印；`--native` 与解释器输出逐行一致；子集外脚本回落且输出一致；二次执行命中缓存。
- `tools/check_fmt_all.py` **207/207**；`tools/verify_claims.py` **22/22**。
- 原生启动器手动验收：绝对路径、相对路径（经 `impor.bat`）、非 .impor 命令透传、字符串脚本回落，全部通过。

## 复现

```powershell
# 1) C 级产物
python Impor.py build cmp_fib25.impor -o fib.exe --no-cache
.\fib.exe

# 2) run 走原生启动器（第二次起是热执行）
.\impor.bat cmp_loop1m.impor

# 3) run 的 Python 入口 + 透明编译
python -S -I -X utf8 Impor.py run --native cmp_loop1m.impor

# 4) 原状解释器
python -S -I -X utf8 Impor.py run cmp_loop1m.impor
```

计时请用 `hbench.exe <次数> <exe> [参数…]`，别用 PowerShell 管道包一层（那会多算 15–20 ms 的壳开销，两组数字不可比）。

## 边界

- `--native` / 启动器只覆盖快路径子集（整数、整数循环、浮点、多参数 print、顶层函数等）；字符串、容器、类、模块、异常仍走解释器，行为不变、速度不变。
- 启动器是 Windows 实现（`_wspawnv` / Win32）；Linux/macOS 上 `impor.bat` 不存在，`--native` 仍可用（Python 入口 + gcc）。
- 需要 `IMPOR_PYTHON` 或 PATH 里有 `python`/`py` 供“未命中缓存时编译”；命中缓存的热执行不需要 Python。

## 附录 A：把解释器内核“下沉到 C”能到多快（2026-11-21 实测）

同口径（进程内 QPC，不含进程启动；工作量与基准一致）：

| 形态 | 100 万次累加 | `fib(25)` |
|---|---:|---:|
| C（gcc -O2） | **0.24 ms** | **0.24 ms** |
| 朴素 C 字节码 VM（手写 `vm.c`，20 条指令，栈式 switch 分派，无 JIT） | **17.2 ms** | **5.4 ms** |
| CPython 自带字节码 `for i in range(N)` | 31.4 ms | — |
| CPython 自带字节码 `while` | 102.7 ms | — |
| ctypes **逐步**下沉（每迭代过边界调 2 次 C 函数） | **986 ms**（单次边界 445 ns） | — |
| Impor 解释器（2061 ms 扣掉约 186 ms 启动） | ≈ 1875 ms（每迭代 1.9 µs） | — |

两条方向相反的结论：

1. **每步调底层反而更慢**：一次跨边界 445 ns 比 CPython 一条字节码（几十 ns）贵十倍以上，1e6 迭代 986 ms，只比 2061 ms 好一倍。
2. **整体下沉才有效**：把内核换成 C 字节码 VM，百万循环 2061 → **17.2 ms（120 倍）**、`fib(25)` 176.8 → **5.4 ms（纯内核）**；按墙钟（+约 10 ms 启动）为 27 ms / 15 ms，已与 C 的 16.5 / 16.7 ms 同台。注意 C VM 内核仍比编译 C 慢 20–70 倍（17.2 vs 0.24），差距被启动时间掩盖。

代价：等于推倒内核重写（parser + VM + `Val` 语义 + 中文报错 + 全量对拍），数千行 C；现成的低成本替代是 `cfast` 编译快路径（16.3 ms，已平 C）。**除非目标是产品级“解释器也要 C 级”，否则不建议动。**

复现材料（项目目录，未随包分发）：`vm.c`、`assemble.py`（汇编两个基准脚本为 `.vmb`）、`ck2.c`（`volatile` + argv 防常量折叠的 C 内核基准）、`cfun.c` + `bench_bottom.py`（ctypes 逐步/整体对照）。

## 附录 A：把解释器内核“下沉到 C”到底能到多快（2026-11-21 实测）

问题背景：既然 2061 ms 是 Python 层分派造成的，那把解释器直接接到机器层会不会就快了？这句话有两种含义，实测结果相反。

**同口径（进程内 QPC 计时，不含进程启动；脚本工作量与基准完全一致）**

| 形态 | 100 万次累加 | `fib(25)` | 说明 |
|---|---:|---:|---|
| C（gcc -O2） | **0.24 ms** | **0.24 ms** | 纯内核时间，不含约 16 ms 启动 |
| 朴素 C 字节码 VM（本轮手写 `vm.c`，20 条指令，栈式 switch 分派，无 JIT） | **17.2 ms** | **5.4 ms** | 用同一份工作量：`prog_loop.vmb` / `prog_fib.vmb` |
| CPython 自带字节码（`for i in range(N)`） | 31.4 ms | — | 同一个 CPython 运行时，仅语言层循环 |
| CPython 自带字节码（`while`） | 102.7 ms | — | 模块级全局名读写，更慢 |
| **ctypes 逐步下沉**（Python 每迭代过边界调 2 次 C 函数） | **986 ms** | — | 单次跨边界 **445 ns** |
| Impor 解释器（2061 ms 扣掉约 186 ms 启动） | ≈ 1875 ms | — | 每迭代约 **1.9 µs** |

**结论（两条，方向相反）**

1. **“每一步都直接调底层”会更慢。** 一次 ctypes 边界调用 445 ns，是 CPython 自己一条字节码（几十 ns）的十倍以上，也吃掉了 Impor 每迭代 1.9 µs 的大部分余量；1e6 迭代实测 986 ms，只比 2061 ms 好一倍。边界成本不是免费的，把粒度切到单操作就等于把解释器的分派开销换成了调用开销。
2. **“整体下沉”才是真解，而且真的能到 C 量级。** 解释器慢的根因不是“离机器远”，而是每一步都在 Python 里做 AST 分派 + `Val` 对象装箱；把内核换成 C 字节码 VM 后，百万循环 2061 → **17.2 ms（120 倍）**、`fib(25)` 176.8（含启动）→ **5.4 ms（纯内核）**。按墙钟算：C VM 约 17.2 + 10 ms 启动 ≈ 27 ms，fib 约 5.4 + 10 ≈ 15 ms，已在 C 的 16.5 / 16.7 ms 旁边，而不是身后的 125 倍。
3. **C VM 与编译 C 仍有 20–70 倍内核差**（17.2 vs 0.24、5.4 vs 0.24）：分派成本、栈机访问、无寄存器分配。这解释了为什么“能到 C 的墙钟水平、但内核仍慢一个量级”——墙钟被启动时间盖住了。

**代价（为什么本轮不做）**

- 这等于**推倒内核重写**：Impor 现在的解释器是 Python 里的完整语言实现（词法/语法/求值/`Val` 语义/模块/异常/中文报错/格式化/对拍门禁），换成 C VM 要重写整套 parser + VM + 错误信息，并把“解释器 vs 产物”的逐行一致性门禁从 24 个用例扩到全量。工程量是数千行 C，且每个语义细节都要重新对齐。
- 现成替代：`cfast` 快路径已经把“能吃的收益”用“编译而非解释”吃掉了（16.3 ms，1.02× C）；`run --native` 与启动器把这条路接到了命令层（38–40 ms）。要让**未命中缓存、不可编译的脚本**也快，只有重写内核这一条路。
- 判断：一次性收益 120 倍，但换来一个与现有 Python 实现并行的第二套语义实现，长期维护成本高。**除非目标是产品级“解释器也要 C 级”，否则不建议动。**

复现材料（本轮在项目目录，未随包分发）：`vm.c`（C 字节码 VM）、`assemble.py`（把两个基准脚本汇编成 `.vmb`）、`ck2.c`（带 `volatile` + argv 的 C 内核基准，防常量折叠）、`cfun.c` / `ctypes` 逐步对照脚本 `bench_bottom.py`。
