# 替代路线图（一步一步走，每步有硬门槛）

> 目标不是“让 Impor 更好”，而是**让某一群人真的从别的语言迁过来**。
> 原则：每一步都留下可复跑的数字；门槛不达标，不进下一步。

## 选定对手：Python 的“脚本分发位”

不替代 C（无指针/线程/LLVM，`docs/3.13-后端能力边界.md` 已明确），不替代 Python 全生态（无 PyPI 规模、无 C 扩展 ABI）。
只吃 Python 的一个痛点：**写个小工具，想给别人用，就得让对方装 Python 或背 30 MB 的 PyInstaller 包**。

现有证据（`docs/替代记分牌.md`，由 `python tools/replacement_score.py` 生成）：

| 指标 | Impor C 后端 | Python（解释器 / 同规模脚本） |
|---|---|---|
| 分发体积 | 125–128 KB 单文件 exe | 需要 Python 环境，或 PyInstaller 30 MB 级 |
| 启动+运行 | 31–40 ms | 232–259 ms（解释器路径） |
| 构建耗时 | 0.5–0.6 s（tcc） | PyInstaller 数十秒 |
| 输出一致性 | 10/10 与解释器逐字节一致 | — |
| 构建成功率 | 10/11（`import math` 被拒） | — |

前瞻结论：**体积 1/250、启动 1/7、零环境依赖**——这就是要对外讲的那句话。

---

## 第 1 步：把“记分牌”立起来（已落地）

动作：

1. `tools/replacement_score.py`（已加）：11 个代表用例 × 三条路径（解释器 / 转译 / C 后端），记体积、构建耗时、启动耗时、输出一致性；产物与转译产物都跑两遍取最快，避免杀软首读噪声。
2. `tools/support_matrix.py`（已在）：16 个能力项的端到端能力矩阵。
3. `docs/替代记分牌.md`、`docs/能力矩阵.md`（已生成，标“请勿手改”）。

验收：

- `python tools/replacement_score.py` 一条命令出表，退出码 0（有不一致就返回 1）。
- `python tools/support_matrix.py --check` 返回 0。

**门槛**：这两条命令在别人机器上也能复跑出同样的量级（不要求毫秒级一致）。

---

## 第 2 步：让“真实脚本”能编译（当前卡点）

现状：`examples/stdlib.impor` 被 C 后端编译期拒绝，因为 `import math` 这类**宿主模块**没有静态实现。
这是所有真实脚本撞到的第一堵墙。

动作（按顺序，每个只做最小可验证块）：

1. **宿主模块静态化**：`math`、`random`、`time`、`path` 四个先做。
   - `impor/ctrans.py` 的 import 分支：把 `import math` 映射成 `rt_math_*` 调用，而不是报“不支持”。
   - `impor/c_runtime.c`：补 `rt_math_sqrt/pow/floor/ceil/abs/pi` 等最小集合。
2. **标准库补厚**：`re`（最小匹配）、`csv`（读写）、`file`（已有 fileread/filewrite）、`path`（join/base/name/ext）。
   - 每个模块都要在 `tools/support_matrix.py` 里加一条用例，拒绝也要在矩阵里可见。
3. **拒绝信息友好化**：不支持时给出“替代写法”，而不是只说“编译期拒绝”。

验收：

- 能力矩阵 C 后端 ≥ 15/16。
- 记分牌新增 10 个“真实脚本”用例（不是语言演示），≥ 8 个构建成功、输出与解释器逐字节一致。

**门槛**：10 个真实脚本里，没有一个以“后端不支持”失败超过 2 次。

---

## 第 3 步：迁移工具（把“愿意试”的人拉进来）

动作：

1. `py2impor` MVP：只做 80% 常见语法（`print`/`for`/`if`/函数/类/`list`/`dict`/`try`），未支持语法输出“此处需手工改”。
2. `impor check --migrate`：同一脚本两边跑，输出 diff；差异为空才算迁移成功。
3. `docs/从 Python 迁移.md`：一张差异表（哪些能自动转、哪些要手改、哪些别迁）。

验收：

- 10 个真实脚本 ≥ 8 个转换后既能 `build` 又能输出一致。
- 差异表覆盖第 2 步所有被拒用例。

**门槛**：任意一个外部脚本，用户能在 30 分钟内完成迁移并拿到 exe。

---

## 第 4 步：从“能出 exe”到“能被别人调用”

动作：

1. `build --lib`：导出 `.a/.dll` + 稳定 C ABI + 头文件（目前只出 exe，这是路线图文档里的 P0）。
2. 提供一个 C 程序调用 Impor 代码的最小示例（`examples/cabi_demo`）。
3. exe 标配：图标、版本信息、`--onefile`、退出码约定。

验收：

- 一个 C 程序能链接并调用 Impor 导出的函数，示例进 `docs/ci-evidence.md`。
- 记分牌体积仍 ≤ 200 KB、启动 ≤ 40 ms。

**门槛**：外部项目可以把 Impor 当“脚本层”接进自己的构建，而不只是跑一个 exe。

---

## 第 5 步：借生态，不造生态

动作：

1. Python 桥：`import python "json"` 这类按需开关（默认关，避免把“零依赖”卖点丢掉）。
2. 精选 5 个高频依赖（`requests`/`csv`/`re`/`datetime`/`sqlite3`）给出“能用什么、不能用什么”。
3. 明确立场：桥是过渡，不是承诺；什么时候用桥、什么时候用 std。

验收：5 个依赖场景跑通，且文档写清“桥 = 依赖 Python”。

**门槛**：用户不会因为“没有某个库”直接放弃，也不会误以为 Impor 是零依赖（用了桥就不是）。

---

## 第 6 步：对外证据与推广

动作：

1. 公开对照页：10 个脚本 × 4 指标（体积/启动/构建/内存），数据由脚本生成。
2. 迁移指南 + 三个真实小工具案例（文件批处理、CSV 报表、JSON 转换）。
3. `docs/compatibility.md` + `api_baseline.json` 的“3.12–3.14 不删不改义”承诺对外发布——这是别人敢迁的底气。

验收：陌生人只读文档就能复现所有数字，并能跑通一个案例。

**门槛**：出现 3 个外部使用者（哪怕只是小工具），才算“开始被替代”。

---

## 不要做的事（写下来防止走偏）

- 不做“更简洁的 Python”：语法已经比 Python 多了一堆同义写法，继续加别名没有收益。
- 不做“可替代 C 的系统语言”：指针/union/线程/LLVM 补齐成本远超收益。
- 不承诺“四端逐位等价”：C 后端是语法子集，拒绝要写清楚（矩阵里已有 0 违例的契约）。
- 不在第 2 步之前做推广：现在拿出去，用户第一条 `import math` 就会走。

## 附：关于“替代 Rust”（结论：不要正面替代，可以侧翼接管）

Rust 的价值不是“快”，而是**在没有 GC 的前提下证明内存安全**（所有权/借用检查 + 零成本抽象 + 无运行时）。
Impor 现在的值模型是动态 `Val` + 类/闭包，缺静态类型、缺所有权语义、缺 trait/泛型、缺 LLVM 原生代码生成——
这些不是补丁能补的，是要重做编译器前端与内存模型。所以：

- **不要碰 Rust 的系统编程位**（内核/驱动/嵌入式/高性能库/并发原语）。
- **可以接管三个侧翼场景**：

| 场景 | 现在谁在占 | Impor 的切入点 | 需要先做完哪一步 |
|---|---|---|---|
| 写 CLI 小工具的人（嫌 Rust 编译慢、产物大） | Rust / Go | 0.5 s 构建、约 126 KB 单文件、零环境依赖 | 第 2 步（宿主标准库）+ 第 4 步（图标/单文件） |
| 在 Rust 程序里跑用户脚本/规则/配置 | Lua / Rhai / 各类脚本引擎 | 把 Impor 做成 Rust 程序的脚本层（`extern "C"` + FFI） | 第 4 步（`build --lib` 出 `.a/.dll` + 稳定 C ABI） |
| 被 borrow checker 劝退的初学者 | 流失到 Python/Go | 承接“想学系统编程但卡住”的人 | 第 1、2 步 + 教学材料（已有教师讲义） |

- 如果坚持走“靠近 Rust”的路线，最小可行台阶（每级都要验收，不许跳）：

1. **静态类型检查**：现在注解只解析后丢弃（`docs/类型注解边界.md`）→ 先做“注解与实参/返回值一致性检查”，只报错不改代码。
2. **确定性内存**：把 `Val` 引用计数暴露成可观测的 `own`/`borrow` 语义，先只对“文件/连接”这类资源做确定性释放（`defer` 已有）。
3. **无运行时**：把 `c_runtime.c` 里的异常、字符串、容器拆成可按需裁剪的模块，做到“纯算术程序不带容器代码”。
4. **原生代码生成**：tcc → LLVM，拿到真正的优化与跨平台目标。
5. **生态桥**：能调用 C 库（已有 FFI 白名单雏形），再谈 crates。

按当前体量与人力估，这条线是**年**级工程；而在第 1~4 步做完之前，Impor 拿 Rust 用户没有任何胜算。

**建议写法**：对外不说“替代 Rust”，说“和 Rust 搭配”——Rust 写核心，Impor 写规则/脚本/工具，零依赖分发。这样既不吹牛，又能真的拿到用户。

## 附二：同时压住 Rust / Python / C / C++ 的唯一交集 —— 做“交付层”

不可能在同一维度上同时赢四家（性能赢不了 C/Rust，生态赢不了 Python，安全语义赢不了 Rust）。
四家**同时弱**的地方只有一个：**把一段逻辑交给别人，让对方立刻能跑、能调用、不用装任何东西**。

| 指标 | Impor（实测） | Python | C / C++ | Rust |
|---|---|---|---|---|
| 交付体积 | **exe 126 KB / dll 97.5 KB** | 要环境，或 PyInstaller 30 MB 级 | 要 CRT/DLL 依赖，装环境容易翻车 | 静态 musl 300 KB–1 MB（强） |
| 构建耗时 | **0.13 s（dll）/ 0.55 s（exe）** | 无构建（但分发要打包） | 构建系统复杂，链接慢 | 秒级到分钟（冷编译） |
| 冷启动 | **33 ms** | 约 250 ms | 约 5 ms（强） | 约 5 ms（强） |
| 被 C/C++ 调用 | **`.h` + `.dll`，已实测** | 要嵌解释器 | 本职 | `extern "C"` |
| 被 Rust 调用 | **同一套 C ABI** | 要 pyo3 + 环境 | 本职 | — |
| 被 Python 调用 | **ctypes 直接调**（项目已有 cabi 测试） | — | 要编译 | 要编译 |
| 学习成本 | 低（小时级） | 低 | 高 | 高（borrow checker） |

结论：**Impor 不该做“第五种主语言”，该做四家共用的“逻辑层/交付层”**——
业务规则、校验、报表、小工具用它写，用 `build --lib` 出 `.dll + .h` 给 C/C++/Rust/Python 宿主调用；
或者用 `build` 出 126 KB 单文件给最终用户双击。宿主语言继续干它们擅长的事。

已实测证据（本轮在桌面工程里跑出来的，不是推测）：

- `export def add(a: int, b: int) -> int` 等三个函数 → `build --lib` 产出 `probe.dll`（97.5 KB）+ `probe.h` + `.def`，0.13 s，导出 `impor_add / impor_fib / impor_greet`。
- 用内置 tcc 编了一个 C 宿主，`LoadLibrary` + `GetProcAddress` 调用：`impor_add(2,3)=5`、`impor_fib(10)=55`、`impor_greet("rust")="hi, rust"`，`impor_free_str` 正常释放。
- 但**`FreeLibrary`/进程退出时崩溃（0xC0000005）**：调用本身没问题，卸载时挂。这是“逻辑层”定位的头号阻塞，必须修。

本条线要过的四道关（不达标就不要对外说“能被宿主调用”）：

1. **修 `FreeLibrary` 崩溃**：定位 DLL 里 atexit / 全局析构 / tcc CRT 混用，做到“宿主加载→调用→卸载→退出”全程干净、退出码 0。
2. **64 位产物**：内置 tcc 只出 i386；`--target win64` 依赖 cl/gcc。要么随包带一个 64 位工具链，要么把 64 位做成默认（现在 64 位宿主无法加载 32 位 dll，等于一半机器用不了）。
3. **Linux 产物**：`--target linux64` 需要 gcc；至少在 CI 里跑通一次，否则“跨平台交付”是空话。
4. **落地示例**：`examples/cabi_demo/`（C 宿主 + Rust 宿主 + Python ctypes 各一份），进 `docs/ci-evidence.md`。

只要这四道关过了，Impor 的位置就没人抢：Rust/C++ 用户不会拿它写核心，但会拿它写插件/规则/小工具；Python 用户不会放弃生态，但会把“要分发的小脚本”搬过来。
