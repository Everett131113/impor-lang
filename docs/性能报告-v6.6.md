# v6.6 性能报告：`run` 默认走原生（P0）+ DLL 启动器（P1）

> **历史内部性能报告标签，不是发布版本号。** 对外发布仍为 `4.0.0`；`v6.6` 只用于性能对照。

- 日期：2026-11-21
- 计法：自写 `hbench.exe`（`CreateProcess` + `WaitForSingleObject` + `QueryPerformanceCounter`，7–10 次取最优）。**不用 PowerShell 的 `&` 直测**，那会多算 15–20 ms 的管道开销。
- 本机：Windows x64；Python 3.11.5（`D:\编程软件\python3.11\python.exe`）；gcc 4.8.1（TDM64，`-std=gnu99`，x64）。
- 基准脚本（与跨语言那轮同一份）：`cmp_loop1m.impor` = `var s = 0 / for i in range(1000000) / set s = s + i / print(s)`；`cmp_fib25.impor` = 朴素递归 `fib(25)`（24 万次调用）。
- 本轮目标（用户原话：「开始 P0,P1」）：**P0** = `impor run` 默认就走原生，别让用户记 `--native`；**P1** = C 后端增加 DLL 模式，启动器在本进程内 `LoadLibrary` 调用，省掉第二次进程创建。

## 结论先摆

| 路径 | 100 万循环 | `fib(25)` | 说明 |
|---|---:|---:|---|
| C（gcc -O2，手写基准） | 16.5 ms | 16.7 ms | 物理下限参照 |
| `impor build` 产物（gcc -O2） | 16.9 ms | 16.3 ms | 已与 C 同量级（patch5 起） |
| **`impor-fast.exe <脚本>`（patch7，热执行）** | **25.1 ms** | **25.6 ms** | P1 成果：38.1 / 39.7 → 25 左右，**1.5–1.6×** |
| **`impor run`（patch7 默认＝原生）** | **207.4 ms** | **192.4 ms** | P0 成果：2132.4 → 207.4，**10.3×** |
| `impor run --no-native`（纯解释器） | 2132.4 ms | 187.1 ms | 参照：CPython + AST 遍历的地板 |
| `noop.exe`（空进程） | 18.6 ms | 18.6 ms | **进程创建地板**，谁都不可能低于它 |

三句话说完：

1. **P0 真的有用，但只在长循环上明显。** 百万循环 2132 ms → 207 ms；`fib(25)` 是 187 → 192 ms（+5 ms，噪声级），小脚本 `print(1+2)` 是 174 → 177 ms（+3 ms）。原因很直白：原生路径要付一次产物进程创建（≈18 ms），省掉的是解释器里 12–14 ms 的 AST 遍历——小脚本上这两笔几乎抵平，长循环上省掉的才是大头。
2. **P1 落到 25 ms，没到预估的 18–22 ms。** 25 ms 里 18.6 ms 是进程创建地板，剩下 6–7 ms 是脚本哈希 + `LoadLibrary` + `impor_entry` 调用 + 两次依赖解析（`SearchPath` 找 python）。地板之上只剩 6 ms 可谈，再往下压就得做常驻服务（P2），那是另一条路。
3. **不要把 25 ms 当成“追上 C”。** 追上 C（16.5 ms）的只有 `impor build` 的产物；`impor run` 这条命令天然带一个 Python 或产物的进程创建，25 ms 是这种形态的下界附近，不是 16 ms。

## P0：`run` 默认原生

做了什么（`impor/cli.py`）：

- `cmd_run` 默认 `native=True`，只有 `IMPOR_RUN_NATIVE=0` 或显式 `--no-native` 才走解释器；`--native/--fast-run`、`--cc X`、`-O0..-O3` 会把详细提示打开（`verbose`），默认路径不打印任何 `[native]` 字样——用户看到的输出与解释器逐字节一致。
- 子集外脚本静默回落解释器（以前会打印一行提示），语义不变。

**这里踩到一个吃掉全部收益的坑，值得记下来。** 第一版 P0 实测是 loop 342.7 / fib 347.8 / tiny 327.5 ms——比不优化还慢 140 ms。逐段计时（`prof_native.py`）定位到 `_native_run` 每次热跑都调用 `_resolve_build_cc`，里面藏着一次 `gcc --version`，**一次 147.5 ms**。修法是新增 `_native_cache_key(fname, src, opt)`：缓存键只含脚本绝对路径、源码、优化级、四个工具链源码文件的 size/mtime 和版本串，**不含“编译器是谁”**；产物文件存在就直接执行，只有真要编译时才去解析编译器。修完就是 207.4 / 192.4 / 177.0。

代价写在明面上：换编译器后缓存不会自动失效，需删 `~/.impor/run-cache`。这是有意的取舍——热执行的价值全在“不解析编译器”，把编译器身份塞回键里等于把 147 ms 还回去。

### 分段账（为什么是 207 ms）

| 环节 | 耗时 |
|---|---:|
| `python -S -I` 空启动 | 38.5 ms |
| `import impor.cli`（含 ctrans/cfast 等） | 103.7 ms |
| `run` 空脚本地板（前两项 + 解析/分派） | ≈174 ms |
| 命中缓存后启动产物进程 | ≈18 ms |
| 产物自身（百万循环） | ≈0.3 ms |

207.4 ms ≈ 174（Python 启动+导入） + 18（产物进程） + 少量解析。**这就是 `run` 走原生的现实：**
它没法低于“启动 Python 去查缓存”这一步，所以 200 ms 附近是这条路的下界；想彻底绕开，只能走启动器（P1）或常驻（P2）。

## P1：DLL 模式 + 启动器内 `LoadLibrary`

做了什么：

- `impor build --dll <脚本> -o x.dll`：走数值快路径转译，入口从 `int main(void)` 换成 `__declspec(dllexport) int impor_entry(void)`，并在 `return 0;` 前插 `fflush(stdout)`（宿主进程退出前保证输出落地）。`--dll` 与 `--lib`、`--c-source` 互斥；内置 tcc 明确报错（32 位 DLL 不可能被 64 位启动器加载）。
- `tools/impor-fast.c`：命中 `<key>.dll` 就在**本进程内** `LoadLibraryW` + `GetProcAddress(…,"impor_entry")` 调用，不再 `CreateProcess`；并且**不调 `FreeLibrary`**——进程随即退出，省一次卸载。没有 DLL 时落 `<key>.nodll` 标记，以后不再每次白试编译；仍保留 patch6 的 `<key>.exe` + `_P_OVERLAY` 作为第二级缓存。
- **探测静默**：冷跑时那次“试编 DLL”的失败诊断（`build --dll 不支持：字符串只能出现在 print 中…`）本来会漏到用户眼前。现在探测子进程的 stderr 重定向到 `NUL`（`STARTUPINFO` 里 `STARTF_USESTDHANDLES` + 可继承的 NUL 句柄），用户只看到程序输出。

### 实测（10 次取最优）

| 项 | 值 |
|---|---:|
| `noop.exe` 进程创建地板 | 18.6 ms |
| `impor-fast.exe cmp_loop1m.impor` | 25.1 ms |
| `impor-fast.exe cmp_fib25.impor` | 25.6 ms |
| patch6 同一路径（overlay 换进程） | 38.1 / 39.7 ms |
| DLL `LoadLibrary` + `impor_entry` 调用（`dllhost.exe` 内测） | 2.4–3.7 ms |
| 启动器体积（`gcc -O2 -std=gnu99 -s`） | 23,040 B |

25 ms 的成分：18.6（进程创建） + 2.4–3.7（DLL 加载与调用） + 脚本哈希/`SearchPath`/路径解析 ≈ 3–4 ms。
**没到预估 18–22 ms 的原因就是这个加法**：18.6 的地板已经吃掉四分之三，DLL 只要 3 ms 上下，剩下全是簿记。要把簿记也削掉，只有 P2（`impor serve` 常驻，零进程创建）能做到个位数毫秒——但那要求用户先起服务，不再是“双击就跑”。

## 与其它语言同一口径的位置

跨语言那轮（PowerShell 直测、含 15–20 ms 管道开销）的数字只作横向参照，不与本报告的 hbench 数字混排：

| 语言/路径 | 100 万循环 | `fib(25)` |
|---|---:|---:|
| C（gcc -O2） | 18.5 ms | 19.2 ms |
| Impor 构建产物 | 20.3 ms | 20.8 ms |
| Lua 5.4 | 34.9 ms | 41.4 ms |
| Python 3.11 | 241.5 ms | 117.5 ms |
| Node 22 | 153.1 ms | 163.4 ms |
| Impor 解释器 | 2205.9 ms | 228.2 ms |
| Ling | 7218.1 ms | 3892.7 ms |

按这个表，patch7 之后的 `impor <脚本>`（启动器 25 ms）已经**越过 Lua**，站到 C/产物后面一档；`impor run`（207 ms）仍在 Python 之下。两条路径别混着说：用户双击 `.bat` 走的是启动器，用户在终端敲 `impor run` 走的是 207 ms 那条。

## 三个本轮修掉的真缺陷

1. **147 ms 的编译器指纹**（P0 收益被吃光）：`_native_cache_key` 从键里去掉编译器身份，改为“产物存在即执行”。教训——优化前先做分段计时，别信“这步应该很快”。
2. **`const` 改写被快路径放行**：默认原生之后，`const A = 1; A = 2` 被 `cfast` 静默接受，`tools/error_audit.py` 从 20/20 掉到 19/20。修法是在 `_native_run` 开头跑 `_reject_const_mutation(ast)`，命中 `UnsupportedFeature` 就 `return None` 交解释器出完整诊断（位置/为什么/修复/错误码/文档锚点）。默认路径不能因为“快”就降级语义。
3. **探测失败诊断泄漏**：冷跑会打印一行 `build --dll 不支持…`，用户会以为程序坏了。改为把探测子进程 stderr 丢进 `NUL`。

## 边界（诚实标注）

- 25 ms 不是 C 的 16.5 ms，也不是“编译器变快了”；差距全在进程创建（18.6 ms 地板）。
- `run` 默认原生对**小脚本**基本不赚（+3 ms），对**长循环**才赚 10×。没做“含循环才走原生”的启发式——它会让行为按脚本内容变化，语义风险大于 3 ms 收益。
- `run` 的缓存不覆盖编译器身份：换 gcc 请删 `~/.impor/run-cache`。
- `--dll` 不支持内置 tcc（32 位）；字符串脚本、模块导入等子集外脚本走解释器，不静默改语义。
- 冷跑首次仍有 50–60 ms（Defender 扫描 + 首次编译），这是安全软件与编译器，不是 Impor。
- 想再快只有 P2（`impor serve` 常驻，个位数毫秒但需要先起服务）和 P3（重写 C 内核，数千行，本轮没做）。
