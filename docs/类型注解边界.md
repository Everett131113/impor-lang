# 类型注解边界（4.7.0 现状，2026-11-23）

Impor 的类型注解**不是完整类型系统**，但也不是“解析后全部丢弃”。当前是**渐进类型门禁 + 运行期动态语义**：写了标注才检查，不写就全动态。

## 会检查的

`impor/typecheck.py` + `impor/semantic.py` 在 `run` / `compile` / `build` 入口执行，也可以单独 `impor check-types` 跑。`typecheck` 的问题一律 `[FAIL] 类型 ...` 退出 2；4.7 新增的三类默认是 **WARN**（打印 `为什么 / 怎么改` 但不中止），`--strict-types` 才升 ERROR。

基础门禁（3.8.1 起就硬拦）：

- `var x: int = 5` / `const P: str = "a"`：初始化是字面量时，检查字面量类型与注解是否匹配。
- 函数参数：`def f(a: int)` 调用时，实参是字面量或可静态推断的表达式，检查类型是否匹配。
- 函数返回值：`def f() -> int` 中 `return "s"` 或裸 `return` 会报错。
- 参数个数：调用实参数量与声明不一致会报错。
- 泛型调用：`def max2<T>(a: T, b: T)` 同一次调用里 `T` 绑定成两种类型会报 `generic-mismatch`。
- 变量重新赋值：已推断/已标注为 `int` 的变量再赋 `"s"` 会报错。

4.7 新增（`impor/semantic.py`，默认 WARN，`--strict-types` 升 ERROR）：

- `arith-type`：算术两侧类型不可能成立——`"a" - 1`、`[1] * 2`、`str % int`。`size_t` / `handle` / `ptr` / `iq` 与 `bool` 不报（C ABI 里那些是合法写法）。
- `int-range`：整数字面量超出 int64（如 `2**63`、`-9223372036854775808` 之外的边界），把 E1012 从运行期提前到解析后。
- `missing-return`：标注了返回类型、函数体却完全没有 `return`（且不是以 `raise` 结尾）。

判定原则：**只信「确定」的类型**——字面量、本函数作用域里带标注的变量、带返回标注的调用。推不出就返回 `?` 并跳过。
这条原则是踩坑后补的：第一版直接复用 `typecheck._type_of`，而父类会对无返回标注的函数**猜**类型（默认 `int`），
于是自举种子 `bootstrap/imporc.impor` 里 `gen_stmt` 的 `ev`（`var ev = parse_expr()`，实际是字符串）被判成 `int`，
一次报 8 条假警告。现在改为 `_strict_type`，「没标注就别猜」。

```powershell
python Impor.py check-types examples\grade.impor            # WARN 不中止，退出 0
python Impor.py check-types --strict-types examples\grade.impor --json
python Impor.py check-types .                                # 目录递归扫全仓
```

退出码：0 干净、1 有 error（或 strict 下有 warn）、3 用法/文件错误。`--strict-types` 同时也是 `run/build/compile` 的全局开关。

## 不检查的

- 变量经过分支、循环、函数调用后的完整流分析。
- 容器元素类型、联合类型、结构化的可空性；`int?` 只做很浅的兼容判断。
- 运行时强制：解释器不会因为注解在运行时拒绝一个值。
- 类方法调用的参数类型（当前已知缺口，20 条用例里未覆盖，后续单独补）。
- C 后端：普通代码的注解不产生运行期检查；注解只用于 C ABI 导出签名。
- 自举编译器 `imporc`：不共享这套 Python 侧门禁。

## 与 S1 的关系

S1 的目标是让注解**参与编译**，最终支撑 system tier 的单态化、去装箱与栈分配。已经兑现的两步：

- 基础门禁：字面量 / 参数 / 返回值 / 参数个数 / 泛型调用的一致性（`tests/test_annotation_gate.py` 的 **20 条正反用例**锁定）。<!-- -->
- 4.6 起：泛型按调用点字面量单态化；4.7 起**全部参数与返回同为一个标量标注**的普通函数也按标注定型（`def sum_to(n:int)->int` → `gp_sum_to_i64(long long)`），见 [`单态化.md`](单态化.md)。

- 未做：类型驱动的容器/结构体代码生成、跨函数流分析、类方法调用检查、C 后端/imporc 共享门禁。
- 未做：混合标注（`def f(a:int, b:float)`）——当前明确要求全部参数与返回同一种标量，不做隐式统一。
- 未做：内建函数的返回类型不进 `_strict_type` 的信任表（`strcut(x,0,1)` 这类返回 `?`，所以 `strcut(...) - 1` 会漏报）。宁可漏报，不造假警告。

复跑：

```powershell
python Impor.py check-types examples\grade.impor
python -m unittest tests.test_annotation_gate -v
```

## 为什么保留

注解在 C ABI（`export func add(a: int, b: int) -> int`）、教学示例、单态化入口和编译前门禁里都有价值：它能提前抓“字面量写错类型”这类低级错误，也能让编译器生成不装箱的原生函数。但它不能承诺“类型安全”。

## 写法建议

- 需要稳定契约的跨语言边界，写完整注解并走 `--lib` / C ABI 检查。
- 普通脚本可以不写注解；不要因为写了 `: int` 就认为运行时会被强制。
- 想让单个函数拿到原生性能（不装箱）：把参数和返回值全标成 `int`（→ `long long`）或全标成 `float`（→ `double`），函数体内别用字符串/内建，编译器会自动生成原生实例；拿不到就回退擦除版，行为不变。
- 不要把当前门禁当成 system tier 的类型系统；对外按“可交付的小型教学语言”表述。
