# RFC 0008：教科书优化编译器后端（OPTC，寄存器式）

## 1. 为什么要改

Impor 此前的自有后端 NVM 是「栈式字节码 + 虚拟机」，且 IR 层只有常量折叠、死代码消除、
循环不变量外提三项局部优化，缺少教科书（龙书 / Engineering a Compiler）优化编译器的
标志性环节：控制流图、数据流分析、寄存器分配、寄存器式目标代码。这使 Impor 在「编译器
后端技术深度」上停留在解释器形态，无法回答「变量如何落到有限寄存器、寄存器不够怎么办」。

本 RFC 在不依赖任何外部编译器/汇编器的前提下，新增一条独立后端 `optc`，把已有三地址 IR
经过完整的中端与后端流水线变成寄存器式目标码并直接执行，补齐上述环节。

## 2. 变更内容

- 新增公开项：
  - 模块 `impor/optc.py`；CLI 子命令 `impor opt run|dump FILE [-o OUT.asm]`。
  - 后端流水线：基本块/CFG → 活跃变量数据流分析（后向 gen/kill 不动点）→ 线性扫描
    寄存器分配（不足时溢出 spill 到栈槽）→ 寄存器式目标码 → 寄存器机执行。
- 删除/改名的公开项：无。语言表面零变化，不新增关键字、不新增语法糖。
- 受影响的错误码：复用 `BackendError`（不支持特性/超量参数）、`OverflowError`（E1012，
  int64 语义不变）、`ZeroDivisionError`，不新增错误码。

## 3. 影响谁

- 已有脚本/项目：纯新增后端，默认命令行为不变；只有显式调用 `impor opt` 才走该后端。
- C 后端 / 解释器：不改动其代码路径；`optc` 与解释器对拍保证语义一致。
- 编辑器 / LSP / 文档：CHANGELOG、README、能力矩阵与本 RFC 同步；编辑器不直接依赖。

## 4. 兼容与迁移

- 不保留旧写法问题：本 RFC 不破坏任何既有写法，无需迁移。
- 目标机参数：可分配物理寄存器 6 个（R0..R5），参数从 R0 起依次传递。
- 明确边界（编译期 BackendError，不静默降级）：
  - 不支持 list/dict、索引/切片、属性、class、try/catch、import、嵌套函数/闭包、lambda、
    异常、for-in、global 作用域；
  - 函数参数数量超过物理寄存器数（6）先拒绝。

## 6. 决策记录

- 日期：2026-11-26
- 结论：采用线性扫描而非图着色——实现与验证成本低、与顺序代码布局契合，足以教科书式
  呈现寄存器分配；目标采用寄存器式而非直接发射 x64 机器码，先保证流水线完整可对拍。
- 反对意见与处理：
  - 「应直接生成可执行机器码」：PE/COFF 与链接、运行时互操作是独立量级工程，单独立项，
    不在本 RFC 捆绑；寄存器式目标码已包含真实后端的全部分析与分配内核。
  - 「寄存器太少/太多」：6 个寄存器能稳定演示 spill，又不至于过度溢出，参数与局部变量
    共用，符合真实 ABI 扣除保留寄存器后的可用规模。
- 后续：栈传参（解除 6 参数上限）、图着色/SSA、以及在本流水线之上发射真实 x64 机器码，
  分别独立评估。
