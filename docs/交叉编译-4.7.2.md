# 跨平台交叉编译证据（4.7.2）

> 本机：Windows 11 + Python 3.11.5，**没有** WSL 发行版 / docker / clang / musl-gcc。
> 4.7.1 因此把「Linux/macOS 实编」列为未做。4.7.2 用 Zig 补上了**编译链接**这一环。

## 1. 工具链

Zig 0.13.0（`zig cc` 自带 musl / libSystem，无需单独装交叉工具链）：

```
zig-windows-x86_64-0.13.0.zip   79,163,968 字节
SHA 由 ziglang.org/download/index.json 给出，解压后 zig.exe 直接可用
```

网络实测：官方源单连接 ~31 KB/s；改成 HTTP Range 32 段并行后总吞吐 115 KB/s，
79 MB 约 12 分钟下完。**分段并行下载脚本**：`tools/par_dl.py`（可重入，已下完的段会跳过）。

## 2. 为什么不是「直接 `impor build --cc zig`」

`impor build --cc` 走的是 gcc 命令行形状（`<cc> -std=gnu99 -O3 -flto file.c -o out`），
而 Zig 需要子命令 `zig cc -target <triple>`。产品侧改动会牵进「编译器族识别」，
本版不做；改为**先用 Impor 自己的 C 后端生成 C，再用 `zig cc` 交叉编译**，
这条链路正好也是 `--lib --c-source` 的设计意图（生成源码包，交给目标平台编译器）。

复现脚本：`tools/cross_build.py <src.impor>`，内部调用 `ctrans.c_transpile` 生成完整 C
（含 `main`），再逐目标编译。

## 4. 这次证明了什么、没证明什么

**证明了**：Impor 完整后端生成的 C（含 3562 行运行时）在 **musl** 与 **macOS libSystem** 下
无需任何改动即可编译并链接成功 —— 包括 `_WIN32` 条件编译分支、`#include` 集合、
以及 int64/Val 运行时。4.7.1 的 POSIX 静态审计（`tools/check_posix_port.py`：
39 处 `_WIN32`、31 处有 `#else`、0 处无保护致命调用）这次得到了编译层面的印证。

**没证明**：**运行**。本机是 Windows 内核，无法执行 ELF / Mach-O；没有安装 WSL/docker/qemu-user。
所以「Linux 上跑起来输出正确」这句话本版仍然不能说。要闭环需要：
一台 Linux 机器（或 CI 的 `ubuntu-latest`，`.github/workflows/ci.yml` 已有 Linux job 配置），
把上面 ELF 拷过去 `./demo_03_strings-linux64-musl` 比对输出。
