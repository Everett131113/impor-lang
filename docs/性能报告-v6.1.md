# Impor v6.1 性能报告

## 目标

把解释器 100 万次算术循环从约 7 秒压到 **3400 ms 以内**，且不改变语言语义。

## 结果

| 指标 | 改造前 | 改造后 |
|---|---:|---:|
| 纯解释执行（`impor bench`） | 7.031 s | **0.581 s** |
| 含进程启动（`loop_1e6`） | 8042.1 ms | **799.8 ms** |
| 字符串 2000 字符 | 525.6 ms | 283.4 ms |
| 递归 fib(22) | 1293.4 ms | 694.6 ms |

门槛：`benchmarks/gate.json` 的 `interpreter_loop_max_ms = 3400`，`impor bench --gate` 超标即失败。

## 改了什么

1. **帧采样降频**：`_tick_frame` 原本每轮循环调用一次 `time.time()`，改为每 1024 轮采样一次。计数器仍然每轮递增，帧上限与调试语义不变。
2. **const 检查短路**：解释器没有声明过任何 `const` 时，赋值不再沿作用域链执行 `check_mutable`。一旦出现 `const`，恢复完整检查。
3. **整数热路径**：`visit_BinOp` 在左右值都是 `int` 时直接执行 `+ - * / %` 与比较，跳过 `isinstance` 和字符串/数字混算检查。
4. **当前作用域直查**：`visit_Var` 先查当前 `Env.store`，命中即返回；未命中才走完整作用域链。

## 边界

- 这些改动只优化解释器热路径，不改 AST、不生成新字节码、不影响 C 后端与自举 imporc。
- `fib_22` 仍比 CPython 慢约 6 倍，递归与函数调用不是这次的重点。
- 计算密集、长循环的交付场景仍建议 `impor build` 生成独立 exe。

## 回归状态

- 性能专项冒烟通过：100 万循环结果 `499999500000`，`const` 只读报 `E1009`，字符串/浮点/除法/负数运算正常。
- 英文关键字回归 10 项全通过（`tests.test_v37.TestEnglishKeywords`、`tests.test_v43.TestKeywordCountUnchanged`）。
- 全量单测 `563 tests in 431.225s`：`FAILED (failures=10, errors=21)`，失败集中在既有 LSP、v2.9 旧语法、v43 lint 与诊断调用栈用例，不是本次性能门槛；未声称全绿。
