# Impor 3.7.0 性能改造说明

## 结论（先说清楚）

用户目标是“解释器比 CPython 快约 60 倍”，后降为“至少提升 20 倍”。

本次 3.7.0 真实做到的是：

- 简单脚本快速后端：`impor bench` 从 **0.564s** 降到 **0.176s**，加速 **3.2 倍**。
- 同负载 CPython 3.11.5 为 **0.148s**，快速后端仍略慢于 CPython。
- C 后端原生 exe 为 **0.389s**，主要被 Windows 进程启动/扫描开销占据；执行段已是直接 `long long` 循环，但短基准无法体现。
- 另一组 `benchmarks/bench_impor.py --only arith`（15 万次、含乘法）为解释器 670.2ms、转译产物 80.5ms，**8.32 倍**；这是另一负载，不能当作普遍 20 倍。

**3.7.0 没有达到 20 倍，更没有达到 60 倍。** 本说明和版本说明都按真实数字写，不拿单个负载的 8.32x 冒充 20x。

## 实际改动

1. `impor/interpreter.py`
   - `Interpreter(fast_mode=True)`：简单 AST 走“转译 + 执行”快速后端。
   - `_fast_eligible()` 白名单：含导入/导出/类/异常/匹配/属性/管道等节点时自动回退树遍历。
   - 转译/编译阶段失败才回退；一旦开始执行不回退，避免重复副作用。
2. `impor/transpiler.py`
   - `transpile(..., skip_tick=True)`：快速后端循环不再每轮调用 `tick_frame()`。
3. `impor/cli.py`
   - `impor run` 默认尝试快速后端；`impor bench` 同时打印树遍历、快速后端、加速比、C 后端四项。
4. `impor/ctrans.py`
   - 顶层纯整数紧循环快速路径：识别“整数常量初始化 + while 整数比较 + 同组变量 + - * 赋值”，生成 `long long` 直接循环，结束后写回 `Val`。
   - 只覆盖形状明确的简单循环；其他结构走原通用路径。

## 为什么没到 20 倍

- 纯 Python 树遍历后端每次循环仍有 AST 分发、环境查表、对象分配；3.7.0 的快速后端已经接近 CPython 同负载，但 Python 解释器本身的循环成本仍在。
- 20 倍意味着 100 万次循环约 **0.025s**，比 CPython 还快约 6 倍；纯 Python 后端做不到。
- C 后端执行段很快，但 `impor bench` 通过 `subprocess` 启动 exe，Windows 进程启动/杀毒扫描约 0.3–0.4s，短基准里占主导。把启动开销算进去，无法证明 20 倍。
- 本机没有 `gcc`/`clang`/`cl`/`pypy` 可用，只有项目内置 `tcc`；换原生优化编译器需要先补工具链。

## 验证

- `Impor.py version`：`Impor (I++) 3.7.0`。
- `Impor.py bench`：树遍历 0.564s / 快速后端 0.176s / 3.2x / C 0.389s。
- 快速 run 冒烟：`examples/hello.impor` 输出正常；`_bench370.impor` 输出 `sum = 499999500000`。
- conformance：100/100，`--ci` 退出码 0。
- 版本真源测试：`tests.test_version_source` 通过。
  - **更正（3.7.1，2026-11-15）**：该项在 3.7.0 的干净目录实际为 `FAILED (errors=1)`，原因是测试读取了不随包分发的 `_release3617.py`。本行当时写“通过”属错误记录。3.7.1 已改为文件存在才检查，并实测 `Ran 1 test ... OK`。
- 未跑 584 项全量测试；快速后端只验证了简单脚本路径，模块/类/异常脚本按白名单回退树遍历。
