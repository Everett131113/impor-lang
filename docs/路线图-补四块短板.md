# 路线图：把 Impor 补成能干「难活」的语言

> 目标不是"变成 Go / Rust"，而是让下列四类日常工作在 Impor 里**有一手可用的路径**，并且每条路径都有可复跑的验收标准：
>
> | # | 难活 | 现状（4.3.0） | 4.3 交付的第一增量 | 下一步的第一硬门槛 |
> |---|---|---|---|---|
> | 1 | 需要第三方库（HTTP 客户端、数据库驱动、图像处理） | 18 个纯 Impor std 模块；`impor pkg` 已有 init/install/lock/registry；FFI 内建 `ffi_open/ffi_call/ffi_alloc/...` 三端有映射 | 无（本轮精力在并发） | 三个官方绑定包能跑通：SQLite 读写、zlib 压缩、libpng 解码，各自 `impor run` 一条命令 |
> | 2 | 真并发模型（协程、channel、线程池） | 线程 / mutex / 原子量 + **`std.channel` / `std.pool`（4.3 新增）** | channel（有界/无界、`send/recv/try_recv/drain`）+ 常驻 worker 池，四端一致 | 条件变量内建 → channel 不再轮询；`select`/超时；协程单独评估 |
> | 3 | 模板级抽象 | 擦除式泛型（声明期约束、无单态化、无约束求解） | 无 | C 后端按调用点单态化 `max2<int>`/`max2<str>`，产物里出现两份专用符号 |
> | 4 | 长期多人协作的大型代码库 | `fmt` / `lint` / `LSP` / `api_baseline` / `release-check`；编译是**单 TU 全量转译** | 无 | 增量编译（模块级缓存）把 20 模块工程的二次构建降到 < 1 s；分 TU 编译 + 链接 |

工作量档：**S** ≈ 一两天能出可验收增量，**M** ≈ 一周量级，**L** ≈ 需要专门迭代、不建议塞进补丁包。

## 一、第三方库（HTTP 客户端 / 数据库驱动 / 图像处理）

### 已有底座（别重复造）

- `impor pkg init|install|remove|list|search|lock|check|upgrade|registry`：支持本地目录 / git / 私有源；`install --frozen` 按 `impor.lock` 还原并校验内容哈希；`search` 只扫本地（离线可用）。
- FFI 一组内建：`ffi_open` / `ffi_call` / `ffi_alloc` / `ffi_alloc_str` / `ffi_read_*` / `ffi_write_*` / `ffi_buffer_size` / `ffi_buffers`；编译期有 `ffi_allow.json` 白名单与强类型调用点原型（`impor/ctrans.py` 里 `ffi_protos`）。
- C 后端把 `ffi_*` 映射到 `rt_ffi_*`（`impor/c_runtime.c`）；解释器侧同一套语义。

### 缺的不是"能不能调 C"，是"装得上、跑得动、有人维护"

| 步骤 | 内容 | 档 | 验收 |
|---|---|---|---|
| 1.1 | **绑定的目录约定**：`bindings/<lib>/` 放 `<lib>.impor`（纯 Impor 包装）+ `probe.impor`（自检）+ `README`（DLL 从哪来、许可证）；`impor pkg` 支持把 `bindings/` 作为本地源 | S | `impor pkg install bindings/sqlite3 --path .` 后 `impor run probe.impor` 打印 `sqlite ok` |
| 1.2 | **三个官方绑定包**：① SQLite（`sqlite3_open/prepare/step/column_*/finalize`）② zlib（`compress/uncompress`）③ libpng（读 IHDR + 解 RGBA8） | M | 每条都有 `examples/`：建表插入查询回读、压缩 1 MB 往返字节相同、PNG 解码宽高与逐像素校验和 |
| 1.3 | **二进制解析策略**：`ffi_open` 找不到 DLL 时按「包目录 → 系统 PATH → `IMPOR_LIBS`」三级查找并给出可操作报错（打印试过的路径） | S | 故意改名 DLL，报错里能看到三级路径全部列出 |
| 1.4 | **图像"处理"而非"解码"**：`std.image` 只做像素级操作（缩放/灰度/裁切/阈值），底层用 `ffi_alloc` 拿裸缓冲；不承诺 JPEG/WebP 编解码 | M | `examples/resize.impor` 输出 PPM，像素数/均值与 Python PIL 对拍一致 |
| 1.5 | **HTTP 客户端硬化**：现有 `std.http` 是纯 Impor 实现；补重定向、超时、gzip 解压、TLS（TLS 走 FFI 到系统 schannel/openssl，**不在纯 Impor 里手写**） | M | 对 `https://example.com` 拿到 200 与 `content-length`；超时 1 s 的 URL 在 1 s±200 ms 内返回失败而不是挂死 |

### 4.3.1 已交付（1.1 / 1.2 的部分）

- `bindings/README.md` 定了目录约定：`bindings/<lib>/` 放薄 C 层 + `<lib>_bind.impor` + `demo.impor` + `.impor/ffi_allow.json`；每个目录自带一句 `gcc -shared -O2 -o ...` 的构建命令。
- **SQLite3 绑定可用**：`impor_bind_sqlite3.c` 在运行时 `LoadLibraryW` 任意 `sqlite3.dll`（不需要 import lib），把句柄压成 1..8 的整数、结果集编成 JSON；Impor 侧 `bindings/sqlite3/sqlite3_bind.impor` 提供 `load/open/exec/query/error/close`。实测（`demo.impor`，64 位解释器 + `python3.9/DLLs/sqlite3.dll`，版本 3.35.5）：建表 / 插 3 行 / 查询回读 `[[1, '甲', 91.5], [2, '乙', 78], [3, '丙', None]]`，坏表名返回 `no such table:` 而不是崩。
- **zlib 绑定可用**：`impor_bind_zlib.c` 通过 `LoadLibraryW` 调 `zlibVersion/compress2/uncompress/crc32`，用十六进制字符串进出，Impor 侧不接触指针。实测（`bindings/zlib/demo.impor` + 64 位 `zlib.dll`，版本 1.2.11）：`crc32("abc") = 891568578`、40 字节文本压缩到 63 字节并 `roundtrip: True`。
- **坑（写进 README 与注释）**：① 路径里的中文必须走 `W` 版 API，`LoadLibraryA` 按 ANSI 解释会返回 126；② CPython 3.11 自带的 `DLLs/sqlite3.dll` 在本机**直接调 `sqlite3_open` 会访问违例**（ctypes 直调同样崩），3.9 的副本正常——绑定只负责加载，DLL 本身的问题要在文档里点名，不背锅；③ `Dev-Cpp\MinGW64\bin\zlib1.dll` 是 32 位，64 位解释器加载不了，要用 64 位副本（h5py 目录下那个可用）。
- **图像绑定（patch7 完成）**：本机全盘没有 `stb_image.h`，改用 Windows 自带 **WIC**（`wincodec.h`，MinGW 4.8.1 自带）做解码与 PNG 编码，`bindings/image/impor_bind_image.c` + `impor_bind_image.dll` 实测：PNG 1024×1024 读入、取中心像素 `13,18,30,255`、另存 PNG 再读回尺寸一致。
- **HTTP 绑定（patch7 完成）**：`bindings/http/impor_bind_http.c` 走 WinHTTP，TLS 1.2 起、证书校验不关闭、重定向上限 5、响应上限 16 MB；`std.http` 改为「绑定优先 + `curl` 硬化兜底」。实测 `https://example.com`：status 200 / body 577 字节；`ftp://` 被拒。

| 步骤状态 | 说明 |
|---|---|
| 1.1 目录约定 | **已完成**（`bindings/README.md` + 两个目录 + 各自 `ffi_allow.json`） |
| 1.2 三个绑定 | **3/3**（sqlite3、zlib、图像/WIC 实测通过） |
| 1.3 三级查找 | 未做（目前是「绝对路径 → 相对 cwd 补全」两级） |
| 1.4 std.image | **已完成**（第 20 个 std 模块，绑定优先、缺 DLL 不崩） |
| 1.5 HTTP 硬化 | **已完成**（WinHTTP TLS1.2 / 证书校验 / 重定向 5 / curl 兜底） |

不做：自建公共包索引站、依赖求解器（semver 冲突自动回溯）、私有 registry 鉴权体系。理由：这些是"平台"投入，没有社区规模前没有回报。

## 二、真并发模型（条件变量已落地，往下是超时/多路等待与协程）

### 4.3 / 4.3.1 已交付

- `std.channel`：`make(cap)`、`send`、`recv`、`recv_timeout`、`try_recv`、`drain`、`size`、`is_closed`、`close`、`stats`、`empty`/`is_empty`。`cap>0` 有界，满则发送方挂起；空且未关闭时 `recv` 挂起；关闭且排空返回哨兵。
- `std.pool`：`new_pool(n)` / `submit` / `pending` / `shutdown`（返回每 worker 处理数，幂等）；池句柄是整数。
- **4.3.1 条件变量**：5 个内建 `cond_new/cond_wait/cond_wait_ms/cond_notify/cond_notify_all` 四端一致；`std.sync` 提供薄封装；`std.channel` 已从 `sleep(0.001)` 轮询改为条件变量挂起（`close` 会 `notify_all`）。
- 四端（解释器 / `impor compile` 转译 / gcc64 / tcc32）同一份 `examples/condvar.impor` 输出一致：`wake: 1 / sum: 10 / timeout: False / dict: 4 / nil: True None / logic: True`；`examples/channels.impor` 仍是 `sent: 20 / sum: 210 / stats: [20, 20, 0] / workers: 4 / done: 16`。
- 口径（必须一起说）：**解释器与 gcc64 是条件变量真挂起；内置 tcc32 因为旧 win32 头文件没有 `CONDITION_VARIABLE`，退化为「代际计数 + 1 ms 轮询」**。整体仍不是 Go 那种调度器级阻塞；任务分派不保证公平；无 `select`；超时目前只有 `recv_timeout` 一种。

### 往下三步

| 步骤 | 内容 | 档 | 状态 |
|---|---|---|---|
| 2.1 | **条件变量内建** `cond_new/cond_wait/cond_wait_ms/cond_notify/cond_notify_all`；`std.channel` 改用它，去掉 `sleep(0.001)` 轮询 | S–M | **4.3.1 已完成**（tcc32 为退化实现） |
| 2.2 | **带超时与多路等待**：`recv_timeout(c, ms)` 已交付；`select(chans)` 返回 `[下标, 值]`（无公平承诺，先来先返回）仍未做 | M | 一半（超时已交付，`select` 未做） |
| 2.3 | **协程评估（先出结论再动工）**：解释器可复用 `yield` 语法位做 generator；C 侧要么 stackful fiber（Windows Fiber API / POSIX `ucontext`），要么在转译层把协程改写成状态机 | L | 未开始 |

不做：M:N 调度器（把 OS 线程映射到 P 个逻辑处理器并做 work-stealing）。理由：栈切换、抢占点、GC 交互全都踩在"三端一致"红线上；先有 2.1/2.2 的阻塞语义，才谈得上调度。

## 三、模板级抽象（泛型 → 单态化 → 约束）

### 现状

- 4.2 的泛型是**声明期约束 + 运行期擦除**：`def max2<T>(a: T, b: T) -> T` 能写能用，调用点做类型绑定校验（混型报 `generic-mismatch`），但 C 后端里每个 `T` 都是同一个 `Val`，没有专用代码。
- 因此它挡不住"想要零开销抽象"的诉求：泛型版和手写 int 版性能一样，因为根本没有生成第二份代码。

| 步骤 | 内容 | 档 | 验收 |
|---|---|---|---|
| 3.1 | **C 后端单态化**：按调用点实参类型生成 `max2__int` / `max2__str` 专用函数，符号名带类型后缀；同类型多次调用复用一份；未用到的类型不生成 | M | `impor build` 产物里 `nm`/dumpbin 能看到两份符号；`max2(1e18, 2e18)`（float）走专用路径；ablation：单态化后 `fib` 级热循环与手写版本差 < 5% |
| 3.2 | **约束求解（最小版）**：`<T: 可比较>` 绑定到 `interface` 能力（`compare` 方法），调用点检查实参类型是否实现该 interface；不实现就报错而不是运行期炸 | M | `def sort2<T: 可比较>(xs: [T])` 对 `[int]` 通过、对 `[dict]` 编译期报 `constraint-mismatch` |
| 3.3 | **泛型容器的类型参数**：`Map<K,V>` / `Set<T>` / `Queue<T>` 从 `std.collections` 的 dict 版升级为带类型参数的版本；容器内元素类型在调用点校验 | M | `var m: Map<str, int> = ...` 写入 `int` 通过、写入 `str` 编译期报错；`Queue<int>` 的 `push/pop` 不出现类型转换 |

不做：C++ 级模板元编程（编译期计算、SFINAE、concept 组合）、宏系统。理由：需要完整的编译期求值器，投入产出比最低。

## 四、大型多人协作工程化

### 现状（4.3.1 门禁实测）

- 质量线：`tools/check_fmt_all.py` 219/219 通过（跳 21）、`tools/support_matrix.py` 20 用例 / 契约违例 1 条（已知基线）；
- 契约线：`tools/api_baseline.json`（关键词 55、运行时内建 122、std 20 模块，patch7 起）+ `impor release-check`；
- 编辑器：VS Code 扩展 + LSP（`impor lsp`）；
- **短板**：`impor build` 是全量单 TU 拼接，20 个模块的工程每次改一行都要重转译 + 重编；没有模块级缓存，没有并行编译。
- **4.3.1 已做（4.1 的一半）**：构建缓存改到**项目内** `.impor-cache/build-cache.json`（不再用 `~/.impor` 全局表），缓存键改成**递归依赖指纹**——被 import 的模块、包目录、安装目录里的 `impor/std/*` 都会并入哈希（旧版只看入口文件的第一层 import）。实测 `examples/condvar.impor`（依赖 `std.sync` + `std.channel`）：首次 `--no-cache` 2.06 s，第二次命中 **0.19 s**；给 `impor/std/sync.impor` 末尾加一行注释（叶子模块）后，缓存正确失效、重建 1.99 s。
- **未做（patch7 如实保留）**：分 TU（每模块产 `.o` 并行编译 + 链接）、`impor_rt.h` 独立头文件。原因：当前 `gen_program` 把整份 `RUNTIME_C`（全部 `static` 函数与类型）拼进程序段，程序直连 static 符号；要拆必须先导出运行时符号并生成完整头文件，属于结构性改动，本轮未动。现有增量编译仍是「项目内递归指纹 + 整包缓存」，不是模块级 `.o` 增量。

| 步骤 | 内容 | 档 | 验收 |
|---|---|---|---|
| 4.1 | **模块级增量编译**：模块 AST 与 C 片段按 `(源文件哈希, 依赖哈希, 版本, 编译选项)` 缓存到 `.impor-cache/`；命中直接复用 | M | 20 模块工程改 1 个叶子模块：二次 `build` 墙体时间 < 1 s（现基线量一次再报）；改注释不改语义时命中率 100% |
| 4.2 | **分 TU 编译 + 链接**：每个模块产一个 `.o`（符号 `__m_<mod>_<sym>` 已是现成的名字空间），运行时头文件单独出 `impor_rt.h` | M | 20 模块工程 8 线程并行编译，总时间比单 TU 降 ≥ 40%；产物行为与单 TU 完全一致（同一套 19 用例矩阵） |
| 4.3 | **告警与 CI 模板**：`lint` 出 `--warnings-as-errors`；仓库自带 GitHub Actions / 本地 `ci.ps1` 模板（fmt → lint → test → matrix） | S | 故意留一个未使用变量，CI 模板在 `--warnings-as-errors` 下 rc=1 并指出文件行号 |
| 4.4 | **多版本并存**：`api_baseline.json` 已冻结公开面；补一份 `docs/兼容性矩阵.md`（4.0/4.1/4.2/4.3 各版本 API 差异与迁移命令），`impor migrate-cn` 之类迁移工具补齐 v4.2→v4.3 的 std 变更 | S | 用 4.2 工程跑 4.3：`release-check` 只报新增（channel/pool），不报删除/改义 |

不做：自建远程 CI 服务、包签名与供应链审计（SBOM）。理由：先把本地可复跑的门禁做扎实，外网服务等有真实协作者再说。

## 五、优先级建议（如果只能做一件事）

1. **2.2 通道超时 / 多路等待**（M）：`recv_timeout` 已落地，下一步是 `select(chans)`；`2.1 条件变量` 已完成，不再排期。
2. **1.2 三个绑定包**（M）：第三方库这条最短路径其实不是包管理器，而是"官方绑定 + FFI 已经能用"。
3. **4.1 增量编译**（M）：决定"大型工程能不能天天用"的首要因素，跟语言特性无关。
4. **3.1 单态化**（M）：决定"泛型是不是零开销"，但它影响的是性能口碑，不是可用性。
