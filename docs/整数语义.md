# 整数语义（4.5.1 定案）

> 一句话：**交付层只有一套整数语义 —— `int64`**。任意精度不是第二套交付语义，只是解释器的调试档。
> 任何一个执行面都必须对同一份源码给出同一个边界判定和同一个错误码 `E1012`。

## 1. 为什么只有一档

Impor 的整数在四个执行面里跑：

| # | 执行面 | 命令 | 整数实现 |
|---|--------|------|----------|
| 1 | 树遍历解释器（默认档） | `impor run FILE` | int64 闸门（`--int64` 为同一实现，默认即开） |
| 2 | 数值快路径后端 | `impor build FILE`（默认 `--fast`） | C `long long` + `rt_ck_add/sub/mul` 溢出检测 |
| 3 | 通用值模型后端 | `impor build FILE --no-fast` | `Val` 统一值模型，整数分支仍走 `rt_ck_*` |
| 4 | IR → C 后端 | `impor ir FILE --build OUT` | 同一份 `c_runtime.c`，同一组 `rt_ck_*` |

如果允许"解释器任意精度 / 产物 int64"，同一份源码会出现 `impor run` 算得出来、exe 崩掉的情况 ——
这属于**语义分裂**，不是"两种模式"。4.0.1 起默认值就改为 int64，4.5.1 把剩下的半档收口：

- `impor run --big` 仍然可用，但它是**显式调试档**，启动即打印提示，且不接受任何产物路径；
- `impor build --big` **直接拒绝**（exit 3），不做静默降级 —— 静默降级会把"解释器能跑、exe 崩"藏得更深；
- `impor.toml` 的 `int_mode = "big"` 等价于 `impor run --big`，同样只影响解释器。

## 2. 边界与错误码

- 范围：`[-9223372036854775808, 9223372036854775807]`（`LLONG_MIN..LLONG_MAX`）。
- 加法 / 减法 / 乘法 / 取负越界 → `OverflowError`，错误码 **E1012**，四个执行面同一句主文案：
  `整数溢出：超出 64 位有符号整数范围（加法|减法|乘法|取负）`。
- 超界**常量字面量**：在生成期就被拒绝，绝不产出一个运行期才崩的产物。
  - 解释器：字面量闸门（`interpreter.py`）
  - IR→C：`cir._lit_c` 抛 `E1012：字面量 … 超出 int64 范围 […]`
  - 静态预检：`impor check-int FILE`（见下）
- 除法 / 取模的除零不在整数语义里，另有 `ZeroDivisionError`（单独错误码）。
  另注意 `E1013 = MemoryError`，与整数无关，不要混淆。

## 3. `impor check-int FILE [--json]`

回答一个问题：**这份脚本能不能按 int64 交付？** 而不是等 gcc 编译完再报 E1012。

```
$ impor check-int demo.impor
== check-int demo.impor ==
  [PASS] int64 口径可编译：2 个整数字面量，范围 [1, 9223372036854775807]
  [PASS] C 后端 / IR→C / 解释器默认档三处逐位一致
  注：只判定常量字面量；运行期算术溢出由 E1012 在解释器与产物中同一文案报出
```

- 退出码：`0` 可编译 / `1` 有超界常量 / `3` 用法错误。
- 一元负号按组合判定：`-9223372036854775808` 合法，`-9223372036854775809` 非法。
- `--json` 输出机器可读结果（含每处违规的行、列、值与原因）。
- **覆盖边界**：只查常量字面量，不做数据流/区间分析，因此
  `var x = 9223372036854775807; print(x + 1)` 会被判 "可编译"，
  实际在运行时按 E1012 中止 —— 这是刻意的分工：静态查常量，运行期查算术。

## 4. 已知装饰差异（不影响判定）

四个执行面的**边界与错误码**一致，但外层报告格式不同，这是产物运行器与解释器的定位差异，不是语义差异：

| 执行面 | 报错头部 | 退出码 |
|--------|----------|--------|
| 解释器 | 四段式诊断（位置 / 问题 / 为什么 / 修复） | 1 |
| 数值快路径产物 | `ImporRuntimeError: …（加法）[E1012]` + 两行提示 | 3 |
| 通用值模型产物 | `运行错误: 第N行: OverflowError: …（加法）[E1012]` + 四段式 | 1 |
| IR→C 产物 | 同「通用值模型产物」 | 1 |

「为什么 / 修复」两段文案在 4.5.1 起与解释器**逐字相同**（`c_runtime.c` 的 `rt_diag_why/rt_diag_fix`）。

## 5. 迁移清单（从 4.4 / 更早升上来）

1. 若有脚本依赖任意精度：把相关计算写成 `impor run --big` 的调试脚本，或改用 `str`/分块算法把数值控制在 int64 内。
2. CI 增加一步 `impor check-int 主脚本.impor`，把"常量超界"挡在构建之前。
3. 不要给 `impor build` 传 `--big`；它现在会显式失败。
