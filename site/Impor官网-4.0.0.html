读法：编译产物这一档，Impor 与 C 是并列的——循环 18.3 vs 18.5 ms、fib 19.3 vs 17.9 ms，差在进程创建地板（约 19 ms，`noop.exe`）以内，净计算都 < 0.5 ms。 常驻服务 impor serve 每请求 4.52 ms（循环）/ 11.94 ms（fib），是唯一低于进程地板的数字，不能直接跟「C 18.5 ms」比；同形态比是 25.2 vs 18.5。 impor run 落在 Python 同一档，因为它每次都起 Python 再 import 整个 CLI（约 174 ms 固定成本），语言本身没变慢。 表里最后一个 Impor 解释器（run --no-native）垫底，这是纯 Python 解释器的结构性地板，不属于可优化项。

这一版修掉的四条真实缺陷

patch8b 都是拿去用的时候撞到的，不是设计里的假设
① 自举编译器 imporc 花括号块一律报「无法识别的语句 [ } ]」

此前 `if (x) { … }`、`def f(n) { … }` 全部在第 4 行闭合 `}` 上失败，而 4.0 的标准写法就是花括号；诊断文件名还永远打成 `imporc.impor`。

修法：词法前把花括号写法整段归一化成缩进写法（保留文件自己的缩进，只叠加花括号层数），并把 40 处诊断改成真实脚本名。现在 `if / def / while` 的花括号、`} else {` 链、块内注释都过，闭合 `}` 不再报错；纯缩进文件一行不改。

② 命令行 README 写 `impor serve run`，实际不认

参数循环把脚本名当「未知参数」吃掉，走完循环已无位置参数，于是这条命令永远空转。

修法：循环里收集位置参数，`serve run` 用第一个当脚本、其余当参数，只对以 `-` 开头的未知开关报错。实测 `impor serve run 脚本` 直接出结果。

③ 语法表 79 关键字 + 43 内建 = 122 条，README 却写 55 / 101；查「管道」回「没有找到」

表里躺着 12 个 4.0 已物理删除的历史关键字（`func` / `loop` / `let` / `local` …），内建缺一大半，`管道` 这种印在规范里的差异化特性查不到；`exit` 既是关键字又是内建，被字典键吞掉一个身份。

修法：表直接对齐真源 `tools/api_baseline.json`，删过期项、补缺失项、加别名（`管道` / `管道运算符` / `pipe` → `|>`），并给 `exit` 记第二个身份。现在 `impor syntax` 打出 55 关键字 + 101 内建 + 1 运算符 = 157，与 README 首屏同一个口径。

④ 公开面 官网页还停在 3.2.3，当前是 4.0.0

公网托管页是 3.2.3 的技术专题存档，与本版事实已经对不上（版本、性能、语法条目数全是旧的）。

修法：重写这一页（就是你正在看的这页）——只放本版实测、修复记录与边界，不再重复旧版本叙事。页面自带、无外部依赖，可直接传到任意静态托管。

能力与边界：照实写

不把「设计目标」写成「已完成」
自举编译器是子集，不是全语言

`imporc` 认的过程式子集含变量、控制流、函数、常用内建；管道 `|>`、部分较新内建不在它的映射表里，遇到会明确报错，不会静默改语义。

C 后端编译期拒绝 `import`

模块导入走解释器；`use std.*` 的脚本会被挡在完整后端之外，以保证语义一致。已知缺口清单在 `docs/能力矩阵.md`，由 `tools/support_matrix.py` 实测生成。

解释器档的慢是结构性的

纯 Python 解释器不可能到几十毫秒：CPython 启动约 93 ms 加上 AST 遍历。这条路径的价值是「零依赖能跑」，不是速度。
